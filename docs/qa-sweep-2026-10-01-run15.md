### [MAJOR] Settlement — every party but an operator is shown a settlement that went straight from Open to Finalized, because three of the four stage rows are written with a `target_id` that is not a settlement

**As:** `agent@` and `performer.a@` on the Album Release
(`e2e00000-0000-4000-8000-0000000000e1`); confirmed by API for `performer.b@` and `professional@`
too.

**Steps**
1. As `operator@`, run the settlement, **Send for review**, post a comment on the Comments tab,
   then **Add revision** (`POST …/settlement/status {"status":"revised"}`), then **Finalize**.
   Four things happened to these figures, in that order.
2. Sign in as `performer.a@` (or `agent@`, `performer.b@`, `professional@`) and open the same
   event's Settlement workspace.
3. Read the **progress rail** at the top of the Settlement tab, then the **Revision history** panel
   on the Comments tab — and read the comment thread six inches to its left.

**Expected.** The rail and the panel were deliberately put on the same source this week so they
could not disagree (`settlementDocument.ts`: *"the rail and the history under it can no longer
disagree, which is the whole point"*), and `EVIDENCE_FOR_STAGE` ticks a middle stop only when the
feed records it. A stop that is unlit is a claim that the stage never happened. Four stages
happened; the performer was **emailed about the first one** (`notifications` row *"Settlement ready
to review — Check your figures and sign off when they match your books"*).

**Actual.** Every non-operator seat sees exactly **one** of the four:

```
$ for a in performer.a agent professional performer.b co.host; do
    api-as $a GET "/activity?eventId=…e1&typePrefix=settlement.,transfer."   # the panel's own query
  done
performer.a:  ['settlement.finalized']
agent:        ['settlement.finalized']
professional: ['settlement.finalized']
performer.b:  ['settlement.finalized']
co.host:      ['settlement.finalized','settlement.revised','settlement.commented','settlement.pending_review']
```

So on the performer's screen:

- the **rail** reads `✓ Open · ² Pending review · ³ Comments received · ⁴ Revised · ● Finalized` —
  three dim, unvisited stops underneath an active fifth that can only be reached through them;
- the **Revision history** reads, in full, *"Settlement finalized — figures locked"*;
- the **comment thread beside it**, on the same tab, shows a remark dated 29 Sept — the exact event
  the history says never occurred.

Earlier in the same run, before finalize, the agent's screen read
`✓ Open · ² Pending review(dim) · ● Comments received` — a settlement standing **past** a stop the
same widget says it never visited.

**The cause is a mis-typed `target_kind`.** `GET /activity` party-scopes by
`target_kind = 'settlement' AND target_id IN (the viewer's settlement ids)`. Three of the four
writers put something else in `target_id`:

```
$ select type, target_kind, target_id from activity_log where type like 'settlement.%';
 settlement.pending_review | settlement | e2e00000-…-0000000000e1   ← the EVENT id
 settlement.commented      | settlement | 7a0b8007-…                ← the settlement_comments id
 settlement.revised        | settlement | e2e00000-…-0000000000e1   ← the EVENT id
 settlement.finalized      | event      | e2e00000-…-0000000000e1   ← correct, and the only one seen
```

`routes/settlement.ts:2949` writes `settlement.${status}` as `targetKind: "settlement", targetId: id`
(the route param — the event); `:2705` writes `settlement.commented` as
`targetKind: "settlement", targetId: comment.id`. Neither id can ever be in `viewerSettlementIds`,
so the clause is unsatisfiable and the rows are unreachable by any party. Operators see them only
because `activity.ts` lets an operator bypass the kind filter entirely. `settlement.finalized`
(`:4037`) is the one that got it right, and its own comment says why:
*"Event-level, unlike every other settlement row … which is news to everyone on the bill."*
`settlement.overridden` (`:2508`) and `settlement.confirmed` (`:3807`) both pass a real `sid` and are
correct — so the defect is exactly these two writers.

**Evidence:**
`docs/screenshots/qa-2026-10-01-run15/performer-rail-three-unlit-stops.png`,
`docs/screenshots/qa-2026-10-01-run15/performer-revision-history-missing-three.png`,
`docs/screenshots/qa-2026-10-01-run15/agent-rail-unlit-pending-review.png`,
`docs/screenshots/qa-2026-10-01-run15/agent-comments-vs-revision-history.png`, plus the SQL and the
five `api-as.mjs` calls above.

**Scope.** Every account kind except `operator` and `co_host`, on every event, for every one of
`pending_review`, `comments_received`, `revised`, `dispute` and every comment. It reproduces after
the settlement is finalized and before it. The operator's own screens are correct throughout, which
is why the fix commit's own browser check would have passed.

### [MINOR] Holds — `POST /events/:id/hold/rank` will rank an event that is not a hold, demoting the real holds behind a row no queue can see

**As:** `operator@`, API-only (no screen reaches this today — see Scope).

**Steps**
1. Create an ordinary event on 5 Dec 2026 at The Lantern Hall. It is born `draft`.
2. `POST /events/<draft-id>/hold/rank {"holdRank":2}`.

**Expected.** `hold_rank` means a position in a queue, and `holdSiblingsOf` defines that queue as
`status = 'on_hold'` — *"an event that is not a hold is not in the queue, it has the night"*
(`lib/hold-queue.ts`). A draft has no position to take, and taking one demotes somebody who has.

**Actual.** 200, and the queue is rewritten around a row that is not in it:

```
$ …/hold/rank {"holdRank":2}      →  200 {"ranks":[{…e4,1},{7dfc06ac…,3}]}   ← the ranked row is absent
$ select title,status,hold_rank from events where event_date='2026-12-05' order by hold_rank;
   Nordic Synth Showcase | on_hold | 1
   QA15 Hold B           | draft   | 2      ← the draft took 2nd place
   QA15 Hold A           | on_hold | 3      ← a genuine 2nd hold, demoted to 3rd
```

and the hold panel on QA15 Hold A then reads, in the browser:

> **3rd hold** · 2 HOLDS ON THIS DATE · 1st Nordic Synth Showcase · **3rd** QA15 Hold A

Two extra consequences. The route's own response omits the row it just wrote, so
`HoldPlacement.tsx`'s `ranks.find(entry => entry.id === event.id)?.holdRank ?? 1` would report
*"1st hold"* for a hold that got some other number. And cancelling the draft does **not** clear the
rank (`QA15 Hold B | cancelled | 2` afterwards), so the gap is permanent.

**Evidence:** `docs/screenshots/qa-2026-10-01-run15/hold-3rd-of-two.png`; the two calls and the
query above.

**Scope.** API-only today: the rank control is drawn on the hold panel, which only exists for an
`on_hold` event, and the Place-a-hold wizard PATCHes `status = 'on_hold'` **before** it ranks
(`HoldPlacement.tsx`). So this is an unguarded route rather than a reachable journey — which is why
it is MINOR and not MAJOR. The companion rule *is* enforced elsewhere:
`rankForHoldJoiningQueue` short-circuits on `status !== 'on_hold'`, so only this route is missing it.

### QA10-1 — MAJOR — The Budget Planner still takes a co-operator's room hire off the top; the settlement (correctly) does not. The act's fee differs by the exact amount §25.7.1 moved.

**As:** operator (browser seat 1). **Verified twice** — once live, once after a full page reload.

**Steps:**
1. On `QA10 Rental Night`, a confirmed `guarantee_vs_door` deal with Marlo Vance: guarantee SEK 20,000, share 70%.
2. A confirmed `rental` deal of SEK 5,000, `deal_parties.role_in_deal`: **payer = Northlight Presents**, **payee = The Lantern Hall**.
3. Budget Planner → 300 × SEK 400 tickets = SEK 120,000; one `Production cost` of SEK 15,000.
4. Read the planner's derived **Performer fee**. Then Settlement workspace → *Run the settlement* and read Marlo Vance's entitlement.

**Expected:** one number. `decisions.md` §25.7.1 (Daniel, 2026-09-28) rules that a rental whose payer
is a party on the event is a **transfer between its two parties**, and the pool is left alone —
"a party cannot be charged for an agreement it is not a party to". #24.1's own promise, quoted in
`budget-planning.ts`, is that *"the Budget Planner moves with the engine, in the same commit … a
split would otherwise have quoted the forecast one fee and the settlement another"*.

**Actual:**
- Budget Planner: **Performer fee SEK 70,000**, i.e. 70% × (120,000 − 15,000 − **5,000 rental**) = 70% × 100,000.
- Settlement: **Marlo Vance SEK 73,500**, i.e. 70% × adjusted net 105,000, with `ladder.offTheTop = "0"`.
- The gap is **SEK 3,500** — precisely the figure §25.7.1's own hand-check names as the act's movement ("the act −3,500").

**Evidence:** `apps/web/src/components/useBudgetSeed.ts:805` computes
`rentals = deals.filter(d => d.status !== "cancelled" && isRental(d))` and line 823 returns
`splitBase: totalRevenue - sheetCosts - rentals` — **unconditionally**. It never asks whether the
rental's payer is a party on the event, which is the whole of the branch
`reconcile.ts:280` (`theShowPaysForItsRoom`) now makes.

```
settlements.computed (DB):
 The Lantern Hall|entitlement 2075000|held 10500000|net -8425000|offTheTop 0|residual 1575000
 Northlight Presents|entitlement 1075000|held 0|net 1075000|offTheTop 0|residual 1575000
 Marlo Vance|entitlement 7350000|held 0|net 7350000|offTheTop 0
 sum(net) = 0
```
Screenshots: `docs/screenshots/qa-2026-09-28-run10/qa10-planner-fee-70000.png`.

**Scope:** it is in shared plain-TS code (`doorForecastFrom`), so it is not per-account and not per-row —
every event with a named-payer rental forecasts a fee the settlement will not pay. The window is the
negotiation window: the operator agrees terms against a fee SEK 3,500 too low and finds out at settlement.

**The one-line fix, for the report and not for me to make:** `useBudgetSeed.ts`'s `rentals` sum needs the
same question `reconcile.ts:280` asks — sum only rentals with no payer party, or a payer who shares the
residual paying somebody who does not. (Stated from the pool's side, as §25.7.1 insists.)

## 5. Probes that lied

**Five — and the fifth is the whole reason §0 exists.**

**5.1 "An operators-only message leaks to the performer." It does not — I sent the wrong field.**
`POST /events/:id/messages {"scope":"operators", …}` returned **201** and the row landed with
`visibility = 'all'`, and `performerA` could read it. That reads exactly like a scope downgrade. The body field
is **`visibility`**, not `scope` (`routes/messages.ts:30`), so Zod stripped my key and applied the schema
default `"all"` — the row was *correctly* an everyone-message. Re-run with `{"visibility":"operators"}` as the
operator: stored `operators`, and `performerA` then saw **3 of 4** messages. Nothing leaked. What the re-run did
find is real and is filed as QA10-10 — the co-host's `{"visibility":"operators"}` is refused **403 "Missing
capability: budget.view"**. Had I asserted only the 201 I would have filed a phantom MAJOR leak.

**5.2 "A co-host sees only one of its two events." It sees both — I read a truncated string.**
The smoke walk captured `main.innerText.slice(0, 190)` per route, and the co-host's `/events` row for the
Album Release fell past character 190. Combined with a Dashboard that legitimately read `Total events 1`
*before* the invitation was accepted, it looked like the list was under-reporting. Re-read in full: both rows
render, `GET /events` returns both, and the Dashboard reads `Total events 2` after the accept. **No finding** —
and it is precisely the trap the brief names: an absent element is the weakest possible evidence.

**5.3 "The performer picker ignores the search term."** Typing `Marlo` into the wizard's performer field
produced a `MY CONTACTS` list of six suppliers and agencies, none of them matching. That is a debounce race,
not a bug: re-reading the same dialog a moment later, the list was `MV Marlo Vance` alone. **No finding.**

**5.4 "The agent is never told when its act is booked."** True as measured on the wizard-built event — and the
first reading (*"decisions #14 is not implemented"*) was wrong. Building the same shape through
`POST /events` **with `venueProfileId` set** attaches and notifies correctly:
```
event_participants: The Lantern Hall (host) · Marlo Vance (performer, invited) · Astra Booking Agency (agent, invited)
notifications:      e2e-agent | event.participant_added | Marlo Vance is on "QA10 Linked Venue Night"
```
The rule works; the **wizard** is what does not reach it, which is why QA10-5 is written about the wizard and not
about `agent-assignment.ts`.

**5.5 The biggest one: the thing I was measuring moved while I measured it.**
I recorded `git rev-parse --short HEAD` as `26c225d` at the start, as the brief asks, and then treated that
as the version under test for four hours. It was not. Four commits landed from a concurrent session during
the sweep — `6eb72f8` (20:27), `8f109ba` (20:36), `7cf4927` (20:44), `ac20310` (20:45) — and `main` finished
at `ac20310`. Because the API runs under plain `tsx` with no watch, the **server** stayed at its 20:13:35
build the whole time, so I was simultaneously behind the checkout on the API and current on the web app.
Three findings were measured against code that no longer existed (§0).

Nothing in the probes could have revealed this: every request answered, every status was plausible, and a
400 from a stale schema is indistinguishable from a 400 from a live one. What revealed it was `git status`
at write-up time reporting three of my own screenshots as **already tracked** — another session had committed
them. **Read `git log` at the END of a sweep as well as the start, and diff it against the API process's
start time (`ps -o lstart=`).** A commit hash captured once is a claim about a moment, not about the run.

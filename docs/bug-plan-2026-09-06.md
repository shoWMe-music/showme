# The nine unswept tickets

## Real bug, cause found

### N1. The reopen reason is written down and shown to nobody
[123qy9rnh3f](https://app.clickup.com/t/123qy9rnh3f) · urgent

**Reported:** *"Reopening a deal requests for a reason, but the text doesn't
appear anywhere with the collaborator on the other side."*

**Confirmed, and the cause is that it is stored twice and read zero times.**
`POST /deals/:did/reopen` writes the reason into `deals.reopen.reason`
(`routes/deals.ts:856-860`) **and** into the activity row's `summary.reason`
(`:884`). Then:

- `reopen` appears in **no serializer** — `grep reopen apps/api/src/serialize/`
  returns nothing, so the client never receives it.
- The notification body is a fixed string: *"Your confirmation was cleared — the
  agreement needs signing again."* (`:909`). The reason is not in it.

So the reopener types an explanation, the app files it in two places, and the
person it was written for is told only that something was cleared.

**Plan (S).** Serialize `reopen.reason` party-scoped under `deal.view.own`, render
it on the agreement tab, and put it in the **in-app** notification body.

> **Keep the email as it is.** The email deliberately carries no terms
> (`:928-931`): one message goes to every party, and a deal is party-scoped, so it
> names the movement and sends each reader to the screen that can show only their
> own line. A free-typed reason can contain terms. Reason in the bell, pointer in
> the mail — that respects the rule already written there instead of quietly
> breaking it.

### N3. Riders: this is decisions #12 being reversed, not a permission bug
[123qy9rnk1u](https://app.clickup.com/t/123qy9rnk1u) · urgent · `bug`

**Reported:** *"For some reason the logic now thinks only Performers can upload
Rider and Documents, this is false. all Users with edit permission or over can add
files."*

**The code does this on purpose, says so in three places, and cites the decision.**
`operator_full` carries `rider.view` but **not** `rider.submit`
(`packages/auth/src/presets.ts:18-55`). `RidersDocumentsCard.tsx:36-38`: *"The
OPERATOR still cannot submit one, and that part was always right: a rider is the
act's own document (decisions #12), so the host has none of their own to send."*
`useRiderUpload.ts:75-78` says the same. This is not drift — it is the rule.

**But Ran's own example resolves it without touching decisions #12.** The grouping
he asks for is:

```
{Venue Name}   → Technical info, Equipment list, Rules of Behavior
{Performer}    → Tech rider, Hospitality rider
```

Those are **two different objects**. The first column is not a rider at all — it is
the venue's own document about its own building. The section currently models only
the second, so the operator has nothing of their own to upload, and the only way to
give them a button looked like "grant operators `rider.submit`" — which would make
the host a submitter of the act's artifact and break the decision.

**The re-scope: give the operator venue documents of their own.** A rider stays the
act's document; a venue document is the operator's. Both land in the same section,
grouped by who filed them, which is exactly the arrangement Ran drew. Nobody has to
reverse a decision to get what he asked for.

**Plan, four parts:**

1. **Venue/event documents as their own kind**, submittable on `event.edit`. *(M —
   this is the part that answers the reported symptom.)*
2. **Profile documents carry into the event** (tech rider, stage plot, accommodation
   rider). *(M)*
3. **Grouped by collaborator** in the card. *(S, after 1 and 2.)*
4. **A change notifies all sides, naming the document.** *(S — the notification
   spine exists.)*

> **Part 2 has a clause that blocks on the invitation epic.** Ran: *"the documents
> from a collaborator only migrate once they accept the collaboration."* **There is
> no acceptance to wait for** — see N6. Build the operator's own half first; the
> collaborator half lands with D1.

### N8. Sharing availability
[123qy9rnjck](https://app.clickup.com/t/123qy9rnjck) · urgent · `bug`

**Reported:** *"The system doesn't include dates marked as Unavailable as
Unavailable. Of course it should not consider these dates as free!"*

**The path is correct end to end, and has been since 2026-08-26.**
`readProfileBusyTime` unions `profile_unavailability` with imported calendar
entries (`lib/availability.ts`); `GET /profiles/:id/availability` returns it

**But there is one real mismatch that fits his words exactly, and it is visible in

| | Scope |
|---|---|
| **Marking** unavailable | the **acting profile**, always — `useMarkUnavailable.ts:28-31` states this outright, and `:368` passes `activeProfileId` |

calendar in the share modal, or marks a date while acting as a different profile
from the one whose row they are looking at. The block lands on profile A; the share
reads profile B; the date shows free.

**Plan: reproduce first.** As an operator with two venues, mark a date, then share

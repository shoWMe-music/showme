# Audit — running app vs. the specification docs (2026-08-23)

Five parallel auditors drove the **running local stack** (real Firebase-emulator tokens, real
Postgres) and compared behaviour against `PLAN.md`, `docs/decisions.md`, `docs/story.md`,
`docs/agent-representation.md` and the `.claude/skills/*` topic guides. Only **discrepancies**
are listed — anything matching spec was deliberately left out.

**Confidence column:** `verified` = reproduced independently after the agent reported it.
`corroborated` = two auditors found it separately from different angles. `reported` = one
auditor, with a quoted request/response, not independently re-run.

Numbering is stable — use `A-nn` when filing tickets.

**Status (end of 2026-08-23):** P1 (A-01…A-10), P2 (A-11…A-14) and **P3 (A-15…A-24) are fixed and
verified end-to-end** against a freshly migrated and reseeded local stack, driven as the seeded
operator / performer / agent / crew. P4 (A-25…A-34) is untouched — it is a build queue, not a bug
list. A-35 is fixed; A-36 needs a product decision; A-37…A-40 were filed while fixing P3.

## P1 — Money correctness and authorization breaches

### A-01 · Settlement silently pays the wrong split · `verified` · **FIXED 2026-08-23**
The engine reads `share.basisPoints` / `share.share` (`apps/api/src/routes/settlement.ts:100-108`).
The stored data holds `share.splitBasisPoints` + `share.guaranteeAmount`
(`packages/db/src/seed-e2e.ts:746`). No key matches → `weightFromShare` returns `null` → **every
payee gets equal weight**.

- Seeded 60/40 deal `d1` computes **2 500 000 / 2 500 000**, not 3 000 000 / 2 000 000.
- The frozen `confirmed_snapshot` — the legal record both parties signed — says 60/40 while the
  settlement pays 50/50.
- `share.guaranteeAmount` is never read from the share at all.

**Why nothing caught it:** `assertBalanced` (`packages/settlement/src/reconcile.ts:123`) checks
`Σ net === 0` — the *total*, not the *distribution*. A 60/40 deal paid 50/50 balances perfectly.
The unit tests pass because they construct inputs in the shape the engine wants, never the shape
the database actually holds.

> Doc: `PLAN.md:161`, `.claude/skills/settlement/SKILL.md:18`

**Fixed.** `splitBasisPoints` is now the one name across the column, the engine and the stored
jsonb; `share` has a real `.strict()` Zod schema instead of `z.unknown()`; and an unreadable share
**throws** rather than falling back to an equal split. Verified live on the seeded 60/40 deal:
600 000 / 400 000, `Σ net = 0`.

Two things the fix surfaced that are worth their own tickets:
- The seeded "Door Split" deal has `split_basis_points = NULL`, so it takes 0% of the pool and pays
  nobody. The reference split deal cannot pay out — see A-13's fixture problems.
  **Fixed 2026-08-23** alongside the P2 sweep: a party's `share` *divides* a deal, the deal-level
  column *sizes* it, and only the latter is read for `door_split`. A-01's own signed snapshot
  (3 000 000 + 2 000 000 on a 5 000 000 pool = the whole pool, 60/40) fixes the value at
  `split_basis_points = 10000`. Both seeds now take every deal's terms from
  `reference-settlement.ts`, and a guard test fails if any seeded `confirmed` deal yields a zero
  entitlement for its payees. Verified in the browser: the album release pays Marlo **SEK 24,000**
  and Neon Tide SEK 16,000 out of a 40 000.00 pool, the venue keeping the residual 0 — it showed
  **SEK 0** for both performers before.
- Zod strips unknown keys by default, so the first version of this fix accepted the old
  `basisPoints` and stored `share: {}` — silently reintroducing the equal split one layer up.
  `.strict()` is load-bearing here, not stylistic.

### A-02 · An agent can rewrite, reopen or delete any act's deal · `verified` `corroborated` · **FIXED 2026-08-23**
Every route in `apps/api/src/routes/deals.ts` authorizes with
`requireEventCapability(request, deal.eventId, …)` — event-level — and
`PRESET_PERMISSION_SETS.agent` (`packages/auth/src/presets.ts:61-65`) holds `deal.edit` +
`agreement.manage`. There is **no representation lookup in that file**.

Reproduced: renaming and reopening the shared split deal (clearing an unrepresented performer's
signed confirmation); rewriting then `DELETE`ing an unrepresented performer's deal (204); and
creating a deal making the agent **its own entitled party**.

> Doc: `.claude/skills/authorization/SKILL.md:38-41` — *"INVARIANT — per-deal resolution, not an
> event grant… **Never a blanket event-level grant**"*; `docs/decisions.md:340` — the agent
> *"is **never a separate entitled party**"*

**Fixed.** A new `lib/deal-authority.ts` resolves authority per deal, requiring BOTH edges
(the performer's `delegatedToAgentProfileId` stamp AND an active `representations` row covering the
venue's country), re-read per request. Verified live: on a deal where the agent has **no** client,
GET / PATCH / send / reopen are all 404 and the deal is untouched; it is absent from the agent's
list; and an agent participant may now only hold `observer`, so it cannot make itself an entitled
party.

**The shared-split case — also fixed.** The first pass left `reopen` deal-wide, so on a deal where
the agent DOES have a client it still cleared the signature of **Neon Tide, whom it does not
represent**. Product rule confirmed: *an agent may sign and unsign only the performer it manages.*
`reopen` now clears only the lines the caller has standing over — for an agent, its represented
performers' lines; for anyone acting for themselves (the operator on its own deal, a performer on
their own line) the clear stays deal-wide, since renegotiating terms you are a direct counterparty
to invalidates every signature on them.

Verified live on the seeded Album Release split (Marlo 60% / Neon Tide 40% / Lantern Hall payer):
the agent's reopen cleared **only Marlo's** line, Neon Tide's stood (`signed by e2e-performer-b`,
confirmed from Neon Tide's own session), and the deal re-closed to `confirmed` once the agent and
venue re-signed — Neon Tide never had to touch it. The operator's reopen still clears all three.
Guarded by a regression test in `deals.test.ts` ("on a SHARED split it stands behind its client's
line only"), confirmed to fail with the deal-wide clear restored.

## P2 — Broken outright

### A-11 · `DELETE /events/:id` returns 500 for every event · `verified` · **FIXED 2026-08-23**
`audit_log.event_id` FKs to `events` with no cascade, and the create handler
(`apps/api/src/routes/events.ts:150`) writes an audit row pinning every event it creates.
Reproduced: created an event, deleted it → `500`, one audit row holding it.

> Doc: `PLAN.md:654` — *"`DELETE` (host admin)"*

**Fixed.** `audit_log.event_id` no longer carries a foreign key at all — an audit row is history and
must outlive the row it describes, which `target_id` has always done. Cascading would erase the
trail and `SET NULL` would blank the one column that groups a deleted event's trail together, so
both were rejected. The delete handler now also *records* `eventId` on its own audit row (it
previously omitted it as a workaround), keeping a deleted event's create→delete trail queryable by
event id. Three other references would have hit the same wall the moment a row existed:
`invitations.target_event_id` → cascade (an invite to a deleted event is unusable),
`booking_requests.event_id` and `spam_flags.event_id` → set null (both outlive the event).
Migration `0004_event_delete_survives_history.sql`.

Verified live as the seeded operator: created an event through the API — which is what writes the
audit row that pinned it — and deleted it → `200`, the event gone, both audit rows intact.

### A-12 · A performer cannot terminate their representation — 500 · `reported` · **FIXED 2026-08-23**
`unassignAgentFromOpenEvents` (`apps/api/src/lib/agent-assignment.ts:186-215`) hard-`DELETE`s the
agent's `event_participants` row, which `settlements.participant_id` references with no
`ON DELETE`. So **any representation that has reached a settlement compute is permanent**.

> Doc: `docs/decisions.md:325` — *"either party can terminate unilaterally"*

**Fixed.** `unassignAgentFromOpenEvents` now soft-removes (`status = 'removed'`), the vocabulary the
participants route and group unassignment already use and which `authorize()` already excludes. It
was the only hard `DELETE` of an `event_participants` row anywhere in the codebase. Access ends the
instant termination commits, while every money reference — `settlements.participant_id`, transfers,
approvals, a budget line's `collected_by`/`paid_by`/`payee`, `deal_parties.participant_id` — keeps
resolving.

Deliberately **no** `ON DELETE` was added to those references: with no hard delete anywhere, an
accidental one fails loudly instead of orphaning or erasing a settled figure. That invariant is
written into the `event_participants` table doc so it isn't later "fixed" with a cascade. A
second-order bug the soft-remove exposed is fixed too — re-signing an agent after a termination now
reinstates the removed row rather than skipping it, which would have left an agent on the event with
zero access.

Verified live: computed the settlement first so money genuinely referenced the agent's participation,
then terminated as Marlo Vance → `200 terminated`; the participation is `removed` with its settlement
row still resolving, the agent's `GET /events/:id` is now `404`, the performer is no longer delegated,
and a recompute afterwards returns `200` with `Σ net = 0`.

### A-13 · The reference concluded event is unreadable **and** mis-computed · `reported` · **FIXED 2026-08-23**
`GET /events/…e2/settlements` → **500** for operator and performer alike: the seeded
`settlements.computed` jsonb uses `cashHeld` and omits `participantId`/`held`, failing response
validation (`settlement.ts:34-41`).

Its figures are also wrong: the fixture splits 70% of **gross revenue**; the spec splits 70% of
the **pool** (revenue − external costs). The engine is right and the fixture is wrong — a
6 300.00 SEK difference on the platform's reference settlement.

**Fixed.** The seeds no longer state a settlement figure at all.
`packages/db/src/reference-settlement.ts` states the terms and the cash **once** and derives the
snapshot by running the real engine (`reconcile` + `assertBalanced`) — the same functions
`POST /settlement/compute` calls — so a fixture can no longer drift from what compute produces.
The snapshot *shape* was a fourth hand-written copy, so `serializeBreakdown` moved into
`@showme/settlement` and the API re-exports it.

Corrected figures: pool **69 000.00** (78 000.00 door − 9 000.00 production; the 1 800.00 hotel names
the performer, so it is a deductible against her entitlement, not a pool cost), performer
`max(18 000.00 guarantee, 70% × 69 000.00) − 1 800.00 = **46 500.00**`, operator residual
**20 700.00**, `Σ net = 0`, one transfer of 46 500.00. The old fixture's 70%-of-gross gave 52 800.00 —
the 6 300.00 SEK difference the finding names.

Two adjacent fixture defects fell out: `seed.ts` wrote only the *performer's* settlement row, so the
operator had no line on its own event; and the seeded private agent commission named none of the keys
the serializer reads, so it was silently invisible to **both** the performer and the agent.

Verified live: `200` for operator and performer where both got `500`, correctly party-scoped (she sees
one row, not two), and **SEK 46,500** on her Settlements screen in the browser.

### A-14 · Cross-event budget references are accepted, then permanently 500 the settlement · `reported` · **FIXED 2026-08-23**
`POST /budgets/:id/lines` validates only UUID *shape*; the FKs are not event-scoped. A
`collectedBy` pointing at another event's participant is accepted (201), after which
`POST /settlement/compute` returns 500 forever — the cash raises the pool but is attributed to
nobody, so `assertBalanced` throws.

Trivially produced by sending a *profile* id where a *participant* id belongs. Same route: a
non-existent participant → 500 (raw FK violation), `{"amount":"abc"}` → 500 (uncaught `BigInt()`).

**Fixed**, in two halves — the second found by driving the running API rather than the tests.

*Foreign references.* `collectedBy`, `paidBy`, `payeeParticipantId` and `dealId` must now point inside
the event, on create **and** on edit. A cross-event id, a profile id sent where a participant id
belongs, and a dangling id collapse into one 400: distinguishing them would be an existence oracle
over events the caller cannot see, and the remedy is identical either way. `amount` is validated as
minor units in the Zod schema (`/^-?\d+$/`, the spelling `deals.ts` already uses), so `BigInt()` can
no longer throw out of the handler.

*Unattributed cash.* A `revenue` line must name `collectedBy` and a `cost` line must name `paidBy`.
Omitting them produced the **identical** unbalanceable state — `201`, then `500` on every compute
forever — with no foreign id involved, so closing only the foreign-id path would have left the finding
half open. The PATCH rule validates the row the edit *would produce*, catching both a nulled
attribution and a paid-for cost flipped to `revenue`. `payeeParticipantId` stays optional: NULL there
is the off-platform supplier that makes a cost a pool cost.

`assertBalanced` was **not** weakened — `Σ net = 0` remains absolute — but a stored line that cannot
balance now surfaces as a 409 naming the line, the offending field and the `DELETE` that clears it,
instead of a 500 whose body is `{"error":{"code":"internal"}}` and whose cause is in a log the API
does not write. Per the local-data steer, that path is a diagnostic only; reseeding is the cure.

Verified live across all eight cases (four foreign/malformed, two unattributed, plus the payee-less
external cost and a properly attributed line that must keep working). The eight new tests were
confirmed red with the checks disabled.

**What it exposed:** every pre-existing test in `budget.test.ts` was creating *unattributed* lines —
rows that would have bricked a settlement. The suite had been asserting against data the engine could
never reconcile, which is the same "green tests, wrong system" pattern as A-01.

## P3 — Boundary and spec violations

**All ten fixed 2026-08-23**, each re-verified by driving the running stack as the seeded
accounts (real Firebase-emulator tokens, freshly migrated + reseeded Postgres) — not by trusting
the suite. Two migrations carry the schema half: `0005_p3_boundaries.sql` (drops `custom` from
`deal_type`, adds `setlist_shares`, adds `booking_requests.on_behalf_of_profile_id`) and
`0006_offer_dedup_names_the_act.sql`.

### A-15 · `deal.type = "custom"` is still creatable · `verified` `corroborated` · **FIXED 2026-08-23**
Both docs removed it, and `PLAN.md:139` says why — *"free text broke the engine"*. Still present
in `packages/db/src/schema/enums.ts:87` and `apps/api/src/routes/deals.ts:17`.
`POST /events/:id/deals {"type":"custom"}` → **201**.

> Doc: `PLAN.md:139`; `docs/decisions.md:459`

**Fixed.** The value is gone from the Postgres enum (the migration re-labels any surviving row
`performance` — `type` is the at-a-glance grouping, the math lives in `structure`, so the re-label
moves no money). The route no longer hand-copies the list: `z.enum(schema.dealType.enumValues)`
reads it off the column, which is the drift itself — the API surface outlived the schema because
the vocabulary was written down twice. `type` was never patchable, so there is no second door.

Verified live: `{"type":"custom"}` → **400** naming the four allowed values, the identical body
with `"performance"` → **201**. A test pins `dealType.enumValues` to exactly four, so re-adding a
type without a decision fails.

### A-16 · Representations accept any account kind on either side · `reported` · **FIXED 2026-08-23**
No kind check in `POST /representations`. Accepted: agent→**team_and_crew**, agent→operator, and
an **operator profile as the agent side**. The crew case was driven end-to-end: proposal →
accept → `delegatable-events` → assignment, leaving a delegation flag on the crew participant.

> Doc: `docs/agent-representation.md:18,44`; `docs/story.md:57-60`

**Fixed.** The agent side must be `kind='agent'`, the performer side `kind='performer'` — checked
at propose and **again at accept**, because accept is where the agreement becomes binding and a
rule that gates a binding act belongs at the binding act. `assignAgentToEvent` re-checks both
kinds too, so a row that reached the table some other way still cannot stamp a delegation flag on
a crew participant.

This is not a formality: story.md defines `team_and_crew` *by contrast* — crew are paid a fixed
fee, "contrast the agent, who takes a percentage of someone else's income". A representation IS
that percentage, so agent→crew is not a stricter case of the same product, it is a different one.
The 400 says so.

Verified live: agent→crew, agent→operator and operator-as-agent are all **400**, each naming the
rule and the kind it got.

### A-17 · The disjoint-region constraint isn't enforced at accept · `reported` · **FIXED 2026-08-23**
`assertDisjoint` runs in `POST /representations` and the `counter` branch, never in `accept`, and
there is no DB constraint. Two representations proposed while both inactive then both accepted →
**two active agents on `DE` at two different commission rates** (1000 and 2500 bp).
`autoAssignAgentOnPerformerJoin` iterates all active reps, so both get assigned and two
commissions derive off the same entitlement.

> Doc: `docs/agent-representation.md:33,100`

**Fixed.** The invariant is now checked at accept as well, inside the transaction, behind a
`SELECT … FOR UPDATE` over that performer's whole representation set — which is what makes two
*concurrent* accepts safe: the second waits for the first to commit and then reads it as active,
instead of both reading "nobody is active yet". The conflict names the overlapping countries and
the incumbent agent rather than saying "no".

Verified live on the exact repro: two proposals for `DE` raised while both inactive, first accept
**200**, second **409 — "Region DE is already covered by an active representation with agent …"**.

No DB-level exclusion constraint: a partial `&&` exclusion over `text[]` needs GiST, which the
array overlap operator does not support here. The row lock is the guard, and it is the same guard
the propose/counter paths now share.

### A-18 · Commission terms are unvalidated free text · `reported` · **FIXED 2026-08-23**
`commissionableBasis` is `z.string().optional()`, `region` a bare `z.array(z.string())`,
`commissionRate` a bare `z.number().int()`. Accepted: **99% commission on
`"merchandise_and_publishing"`**, a negative rate, and regions `["ATLANTIS","sweden",""]` — where
`"sweden"` silently matches nothing, so the territory looks set but is inert.

> Doc: `docs/story.md:69` — commission is *"**never** on merch or non-live revenue"*;
> `docs/decisions.md:303`

**Fixed**, with the vocabularies in plain modules rather than inline in the route:

- **Territory** — ISO 3166-1 alpha-2, uppercased and de-duplicated on the way in, every entry a
  country that exists. New `packages/shared/src/countries.ts` holds the full alpha-2 register (the
  *whole* register, not the markets we sell in — conflating "a real country" with "a country we
  operate in" would be a different lie). Territory must also say one thing: worldwide **or** a
  non-empty list, never both, never neither.
- **Rate** — integer basis points, `0 < rate ≤ 5000`. Past half the performer's income the agent
  is the principal and the performer the service; that is not representation. The bound is stated
  in the error.
- **Basis** — a closed vocabulary of one, `deal_income`, and the comment says why that is a
  statement about the engine rather than laziness: `settleRepresentation` commissions the
  performer's *whole* event entitlement, so no narrower basis is computable today. Merch and
  publishing are excluded by **definition** (story.md:69) and will never join the list; split
  bases could, the day the engine can attribute an entitlement to a deal component. The old
  behaviour stored `"merchandise_and_publishing"`, displayed it as the agreed basis, and then
  commissioned everything anyway.

Verified live: 99%, negative, `merchandise_and_publishing`, `["ATLANTIS","sweden",""]`,
worldwide-plus-countries and no-territory-at-all are all **400**; `["de","DE"]` normalises to
`["DE"]` and stores `deal_income`.

### A-19 · Future-dated termination takes effect immediately · `reported` · **FIXED 2026-08-23**
The route sets `status='terminated'` and unassigns in the same transaction regardless of
`terminatedEffectiveAt`. A termination dated 2027-06-01 flipped status ~9 months early, and the
agent stops receiving new events during a notice period they are still contractually working.

> Doc: `docs/decisions.md:325-326` — *"effective-dated (immediate or **agreed-future**)"*

**Fixed.** A future-dated termination is now *pending*: both stamps are written, the row stays
`active`, nothing is unassigned, and the agent keeps negotiating and keeps being auto-assigned
onto new in-region events until the moment arrives. Immediate termination is unchanged. A
future date on a merely `proposed` row still terminates at once — a notice period only makes
sense for an agreement someone is working; withdrawing an offer is not notice.

Liveness has **one** answer — `isRepresentationActiveAt(row, now)` — and every reader goes through
it: deal authority, agent assignment, commission settlement, the disjoint checks, the event-grant
gate. A pending termination still blocks a successor on the same region, because it is still live.
The sweep (`reapDueRepresentationTerminations`, wired into the scheduled jobs beside the other
reapers) makes the *stored* state converge; it is never what makes a read correct.

**The gap the live run found.** Correctness-must-not-wait-on-cron held for money and not for
access: with the moment passed and the sweep not yet run, the agent could still *read* the event,
and — worse — the delegated performer was **still view-only**, locked out of confirming her own
deal until cron. That is A-03's deadlock reappearing inside the window this feature created. Both
halves are now resolved in the capability engine itself: `effectiveEventCapabilities` resolves an
agent's standing and a performer's delegation against the representation's liveness, not against
the `event_participants` projection, so the stale rows grant nothing the agreement no longer
backs. `riders.ts` and the hold-decision check were reading the same stale flag and were fixed
with it; `commission-settlement.ts` and `deal-authority.ts` already resolved correctly.

Verified live, in three states of one representation:
1. terminate effective 2027-06-01 → `status: "active"`, both stamps set; the agent still reads the
   event and still holds its client's deal;
2. the effective moment moved into the past **with the sweep deliberately not run** and the
   projection rows physically untouched → the agent's event read is **404** and Marlo **confirms
   her own deal, 200**, immediately;
3. the sweep run for real → representation `terminated`, agent participation soft-removed (A-12's
   vocabulary), delegation flag cleared, performer keeps every open event.

### A-20 · Free-tier event cap is bypassable · `reported` · **FIXED 2026-08-23**
The gate (`apps/api/src/routes/events.ts:202`) fires only on `status === "confirmed"`. At the cap,
`PATCH {"status":"confirmed"}` → 403 ✅ but `PATCH {"status":"concluded"}` → **200**, and
cap-status then reports `used: 4, limit: 3`. The only real monetization limit is one field value
away from unenforced.

> Doc: `PLAN.md:613` — *"**confirm/conclude** event when COUNT ≥ cap → blocked"*

**Fixed.** The counted set is declared once — `CAP_COUNTING_EVENT_STATUSES = ['confirmed',
'concluded']` — and both the COUNT and the gate read it, so the meter and the limit cannot drift
apart again. One helper, `assertEventCapAllows`, is called from every write path that moves an
event *into* that set: the events PATCH and the hold-confirm route. Transitions *inside* the set
and *out of* it are never gated. `POST /events` carries no status (a create always lands on the
`draft` default), commented in place rather than guarded with dead code.

Verified live from a freshly seeded database (2 of 3 used): the exact bypass — `on_hold →
concluded` — takes the third slot, the fourth is **403 whether written as `concluded` or
`confirmed`**, cancelling is never gated, and freeing a slot re-opens exactly one.

### A-21 · No `grant_admin` entitlement gate on participants · `reported` · **FIXED 2026-08-23**
`canUseFeature(…, "grant_admin")` is wired only in `routes/profiles.ts:504,566`;
`routes/participants.ts` never calls it. A free-tier operator assigned `operator_full` to a
performer, who then successfully renamed the event.

> Doc: `PLAN.md:656`, `PLAN.md:615`

**Fixed**, and not only on the route the finding names. PLAN.md:614 states the rule
route-independently — *"assign `operator_full`/admin permission set to a collaborator → requires
host plan ∈ paid"* — so every path by which a permission set reaches an `event_participants` row
is gated: participant create and update, the event invitation that carries a `permissionSetId`
(at **create**, so the inviting host gets the error rather than minting an invitation that dies in
the recipient's hands, **and** at accept, for a plan that lapsed in between), and group assignment
— both the explicit override and the group members' stored defaults, which was a real hole, not a
theoretical one.

"Admin-grade" is defined once, as `participants.manage` / `permission.grant_admin` /
`event.delete` / `members.manage`. `agreement.manage` (every agent holds it), `crew.manage` (every
crew lead) and `templates.manage` are deliberately outside it: paywalling those would paywall
ordinary booking rather than the act of making someone an admin. Plain `event.edit` is outside it
too — PLAN.md:614 draws the line at an admin set, not at edit rights. The charge falls on the
event host's profile, the one whose plan is at stake.

Verified live as the free-tier seeded operator: `operator_full` via participants → **403**, via an
event invitation → **403**, an ordinary crew set → **201**.

### A-22 · Public pages serve `draft` and `cancelled` events and accept RSVPs · `reported` · **FIXED 2026-08-23**
`apps/api/src/routes/public.ts:150,195` filter on `published` only; status is never consulted, and
`POST /publish` has no precondition. A draft event with no date was published and served; after
`PATCH {"status":"cancelled"}` it still returned 200 and **still accepted RSVPs**.

> Doc: `PLAN.md:620` — *"**published+confirmed** events"*

**Fixed.** The public read is `published AND status ∈ {confirmed, concluded}` — a concluded show
keeps its page, because the link is out in the world and the show did happen; everything else is a
**404**, matching the file's existing no-existence-leak doctrine. RSVPs are taken only for a
`confirmed` show: a cancelled one answers **409 "This event has been cancelled"** and a concluded
one **409 "This event has already taken place"** — the page was public, so a reason is honest
rather than a leak. Publishing now requires a confirmed event **with a date** (a dateless page is
not an announcement; door and start times stay optional, "doors TBA" is a real poster state).

`published` is deliberately not recomputed when an event is cancelled — it is the host's
publishing intent, and the read rule is the single gate, so a re-confirmed show does not silently
vanish from the world.

Verified live: draft **404**, cancelled **404**, confirmed **200**, concluded **200**, RSVP to the
confirmed show **200**, RSVP to the concluded one **409**, publishing an unconfirmed event **400**.

### A-23 · Any participant can author a setlist · `corroborated` · **FIXED 2026-08-23**
`PUT /events/:id/setlists` (`apps/api/src/routes/setlists.ts:99-101`) authorizes on
`schedule.view`, which every participant holds. Crew and agent both wrote setlist rows (200).
Reads *are* correctly party-scoped, and there is no route to *share* a setlist — the mechanism
that is supposed to be the crew's only access.

> Doc: `PLAN.md:412`; `docs/decisions.md:628`

**Fixed** as a capability, not a role check. The catalog gained `setlist.author`, held by the
performer preset and the performer **floor** — including the *delegated* floor. That last part is
deliberate and commented: an agent carries business authority, never the songs. Dropping it there
would either deadlock the act (nobody could author) or hand the setlist to the agency, which is
the boundary story.md draws between the two kinds. The ceiling refuses the capability to any event
role but `performer`/`support`, checked *before* the host/co_host short-circuit — a managing
operator is not exempt from the artistic boundary the way it is exempt from the pool ceiling, so
even a hand-written permission set cannot make an operator an author.

The missing sharing mechanism is built (`setlist_shares`): the author — and only the author —
grants read access to another participant on the same event and revokes it; a non-operator's read
returns their own setlists plus anything shared with one of their participant rows; a share aimed
at another event's participant is a 400.

Verified live: crew, agent **and operator** are all **403 `Missing capability: setlist.author`**;
the performer authors; before the share the crew sees **0** setlists, after it **1** (the real
items), after revocation **0** again; the crew cannot share it onward.

### A-24 · Outgoing offers are anonymous and pitchless · `reported` · **FIXED 2026-08-23**
`CreateOfferBody` is only `{targetProfileId, wantedDate, offerFeeMin, offerFeeMax}`; the insert
writes none of `contact_name` / `email` / `artist_name` / `pitch`, and the response has no
`senderProfileId`. The venue's inbox shows a bare date and fee range with no idea who is offering
— and **no field exists through which an agent can name the performer it offers on behalf of**.
The seeded rows show the intended shape, so this is the write path, not the model.

> Doc: `docs/decisions.md:593`

**Fixed.** The offer carries `contactName`, `email`, `artistName`, `pitch`, `note`, `musicUrl` and
`videoUrl` — sanitised and length-bounded the way the public lead form already does it — and the
row is never anonymous: omitted identity fields default from the sending user and profile. The
response and both list directions expose `senderProfileId`, `senderType` and the identity fields,
so the inbox can say who is asking.

The agent case gets the column the finding says is missing: `booking_requests.on_behalf_of_profile_id`,
accepted only from an `agent`-kind profile with a **live** representation of that performer (the
same liveness predicate A-19 introduced, so an offer inside a notice period is fine and one after
it lapses is not) — anything else is a 400, never a silent drop. When set, the act's name leads
and the agency is credited beneath it. The pending-offer dedup index now includes the act
(`0006`), or an agent pitching two different performers to one venue on one night would collide as
a duplicate; only that column is `COALESCE`d, so dateless offers keep the semantics they had.

Verified live, and visible in the browser: the operator's inbox row reads **"Marlo Vance · via
Astra Booking"** with the pitch, a performer's own offer defaults to its own identity, offering
for an unrepresented performer is **400 "You have no active representation for that performer"**,
a non-agent using the field is **400**, and a malformed email is **400**.

## Cross-cutting observations

- **The balance check can't catch distribution errors.** `Σ net = 0` is necessary, not sufficient.
  A-01 is invisible to it, and A-14 is the only settlement bug it *does* catch — by 500-ing.
- **Unit tests pass while the system is wrong.** The settlement suite builds inputs in the
  engine's preferred shape; the mismatch (A-01) lives in the *mapping* between stored data and the
  engine, which nothing tests.
- **Authorization is split across layers despite the skill saying it never should be.** A-04 is a
  bespoke role check that bypasses the capability engine entirely, and it's the one that lets a
  support act cancel a show.
- **A projection is not a permission.** Three of the ten P3 fixes came down to the same shape: a
  materialized row (`event_participants(role=agent)`, a `delegatedToAgentProfileId` stamp, a
  `published` flag) was being read as if it were the rule it was derived from. The fix is always to
  re-derive from the agreement — the representation's liveness, the event's status — and let the
  projection be a cache that a sweep reconciles, never the authority. The A-19 follow-up is the
  clearest case: correctness held for money and failed for access, in the same window.
- **The API has no logs.** `buildApp` sets `logger: false`, so every 500 above arrives with an
  empty payload. Several findings needed the query reproduced by hand to diagnose.
- **The seed is not idempotent under foreign references.** After the audit, `seed:e2e` failed with
  an FK violation because audit-created rows referenced seeded ones. Recovery was to drop the
  container.

## Environment caveats

- Five auditors shared one database and mutated it concurrently; individual findings were each
  re-verified against a live response, but absolute counts (e.g. event totals) drifted.
- The seeded `operator` account has `is_admin = true` — the *only* seed user that does — so
  operator-side results are not a clean operator test. The admin guards themselves are correct.
- `profile_locations` has exactly one row, so cross-region/market behaviour was unprobeable by
  construction.

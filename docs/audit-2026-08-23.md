# Audit — running app vs. the specification docs (2026-08-23)

Five parallel auditors drove the **running local stack** (real Firebase-emulator tokens, real
Postgres) and compared behaviour against `PLAN.md`, `docs/decisions.md`, `docs/story.md`,
`docs/agent-representation.md` and the `.claude/skills/*` topic guides. Only **discrepancies**
are listed — anything matching spec was deliberately left out.

**Confidence column:** `verified` = reproduced independently after the agent reported it.
`corroborated` = two auditors found it separately from different angles. `reported` = one
auditor, with a quoted request/response, not independently re-run.

Numbering is stable — use `A-nn` when filing tickets.

## P1 — Money correctness and authorization breaches

### A-01 · Settlement silently pays the wrong split · `verified` · **FIXED 2026-08-23**
The engine reads `share.basisPoints` / `share.share` (`apps/api/src/routes/settlement.ts:100-108`).
The stored data holds `share.splitBasisPoints` + `share.guaranteeAmount`
(`packages/db/src/seed-e2e.ts:746`). No key matches → `weightFromShare` returns `null` → **every
payee gets equal weight**.

- Seeded 60/40 deal `d1` computes **2 500 000 / 2 500 000**, not 3 000 000 / 2 000 000.
- The frozen `confirmed_snapshot` — the legal record both parties signed — says 60/40 while the
  settlement pays 50/50.
- `share.guaranteeAmount` is never read from the share at all.

**Why nothing caught it:** `assertBalanced` (`packages/settlement/src/reconcile.ts:123`) checks
`Σ net === 0` — the *total*, not the *distribution*. A 60/40 deal paid 50/50 balances perfectly.
The unit tests pass because they construct inputs in the shape the engine wants, never the shape
the database actually holds.

> Doc: `PLAN.md:161`, `.claude/skills/settlement/SKILL.md:18`

**Fixed.** `splitBasisPoints` is now the one name across the column, the engine and the stored
jsonb; `share` has a real `.strict()` Zod schema instead of `z.unknown()`; and an unreadable share
**throws** rather than falling back to an equal split. Verified live on the seeded 60/40 deal:
600 000 / 400 000, `Σ net = 0`.

Two things the fix surfaced that are worth their own tickets:
- The seeded "Door Split" deal has `split_basis_points = NULL`, so it takes 0% of the pool and pays
  nobody. The reference split deal cannot pay out — see A-13's fixture problems.
- Zod strips unknown keys by default, so the first version of this fix accepted the old
  `basisPoints` and stored `share: {}` — silently reintroducing the equal split one layer up.
  `.strict()` is load-bearing here, not stylistic.

### A-02 · An agent can rewrite, reopen or delete any act's deal · `verified` `corroborated`
Every route in `apps/api/src/routes/deals.ts` authorizes with
`requireEventCapability(request, deal.eventId, …)` — event-level — and
`PRESET_PERMISSION_SETS.agent` (`packages/auth/src/presets.ts:61-65`) holds `deal.edit` +
`agreement.manage`. There is **no representation lookup in that file**.

Reproduced: renaming and reopening the shared split deal (clearing an unrepresented performer's
signed confirmation); rewriting then `DELETE`ing an unrepresented performer's deal (204); and
creating a deal making the agent **its own entitled party**.

> Doc: `.claude/skills/authorization/SKILL.md:38-41` — *"INVARIANT — per-deal resolution, not an
> event grant… **Never a blanket event-level grant**"*; `docs/decisions.md:340` — the agent
> *"is **never a separate entitled party**"*

### A-03 · Delegation is a deadlock — a represented performer's bookings become unconfirmable · `verified` `corroborated`
Both sides are locked out:

| Action | Agent | Delegated performer |
|---|---|---|
| Confirm deal | `400 "You are not a party to this deal"` | `403 Missing capability: agreement.confirm` |
| Confirm settlement | `403 Missing capability` | `403 Missing capability` |
| Submit rider | `403 rider.submit` | `403 rider.submit` |
| Post message | — | `403 message.post` |

`DELEGATED_PERFORMER_FLOOR` (`packages/auth/src/presets.ts:174-179`) strips the capabilities;
`PRESET_PERMISSION_SETS.agent` never gains them; `resolveDealViewer`
(`apps/api/src/routes/deals.ts:114-139`) has no delegation traversal.

Control: an **undelegated** performer confirms its own settlement fine (200).

> Doc: `docs/decisions.md:320`; `docs/agent-representation.md:46`

### A-04 · A support act can confirm — or cancel — the headliner's show · `verified` `corroborated`
`requireBookedPerformer` (`apps/api/src/routes/holds.ts:84-104`) accepts **any** participant with
`role ∈ {performer, support}` and consults **no capability**. The handler then writes
`events.status` for the whole event and cascade-cancels competing holds.

Inverted exactly: the delegated performer (read-only by spec) succeeds; the agent (whose job this
is) gets `403`.

> Doc: `docs/story.md:65-66`; `.claude/skills/authorization/SKILL.md` — *"One module; never split
> auth across layers"*

### A-05 · "Locked FX" contradicts the figures it is stored against · `reported`
Conversion happens at **compute** with the live rate (`settlement.ts:170-180`); **finalize**
re-reads the cache and writes today's rate into `data.lockedRates` **without recomputing**
(`settlement.ts:502-528`).

Demonstrated end-to-end: entitlement produced at rate 11.0, snapshot stores
`lockedRates {"EUR":"5.0"}` against it. Replaying the "locked" rate reproduces 500 000, not
1 100 000 — the audit record refutes itself.

> Doc: `docs/money.md:30`, `PLAN.md:258`, `PLAN.md:508`

### A-06 · Private budgets are readable **and writable** by any co-operator · `verified`
`GET /events/:id/budgets` (`apps/api/src/routes/budget.ts:108-131`) selects
`where(eq(budgets.eventId, id))` — no `scope`, no `ownerProfileId` — and `serializeBudget` redacts
nothing. A different profile holding `co_host` + `budget.view` read a private margin line **and
PATCHed it** (200).

> Doc: `PLAN.md:207` — *"private = one operator"*; `PLAN.md:661` — *"shared/private scoped"*

### A-07 · The see-all override the docs dropped is still the mechanism · `corroborated`
`resolveDealViewer` sets `isOperator = capabilities.has("budget.view")`
(`apps/api/src/routes/deals.ts:137`) and `serializeDeal` (`apps/api/src/serialize/deal.ts:66`)
returns **all** party lines for it. `settlement.ts:314` does the same.

Result: the venue reads a performer's private sub-hire (what that performer pays their own sound
tech) — the exact case the decision resolved as invisible.

> Doc: `docs/decisions.md:74-81` — *"PURE party-scoping — no `*.view.all` override… operator not a
> party → invisible"*; `docs/story.md:36` — operators get *"no see-everything god-mode"*

### A-08 · Recompute destroys recorded payment state · `reported`
Compute wholesale `DELETE`s the event's transfers (`settlement.ts:226-236`). A transfer marked
`paid` (version 2) came back `owed` (version 1) on **identical inputs** — row deleted and
reinserted, no 409, no audit of the state change.

Optimistic locking (`docs/decisions.md:173-175`, *"never a silent overwrite"*) guards everything
except the one operation that actually rewrites money.

### A-09 · Finalize doesn't finalize · `reported`
`POST /settlement/finalize` returns a version but never writes `settlements.status` — the
`finalized` enum value is **unreachable through the API**. After finalize, a new budget line was
accepted and recompute silently replaced every figure with no new snapshot.

### A-10 · The private agent commission can only be settled by the operator — who must never see it · `reported`
`PATCH /events/:id/transfers/:tid` requires `settlement.edit` (`settlement.ts:608`), which is in
neither the `performer` nor the `agent` preset. Performer → 403, agent → 403, **operator → 200**,
with the response disclosing the commission amount, the representation id and the performer→agent
direction that `GET /settlements` deliberately filters out.

> Doc: `docs/decisions.md:382-386` — private rows go *"**only** to the performer/agent … and
> **never** to the operator"*

## P2 — Broken outright

### A-11 · `DELETE /events/:id` returns 500 for every event · `verified`
`audit_log.event_id` FKs to `events` with no cascade, and the create handler
(`apps/api/src/routes/events.ts:150`) writes an audit row pinning every event it creates.
Reproduced: created an event, deleted it → `500`, one audit row holding it.

> Doc: `PLAN.md:654` — *"`DELETE` (host admin)"*

### A-12 · A performer cannot terminate their representation — 500 · `reported`
`unassignAgentFromOpenEvents` (`apps/api/src/lib/agent-assignment.ts:186-215`) hard-`DELETE`s the
agent's `event_participants` row, which `settlements.participant_id` references with no
`ON DELETE`. So **any representation that has reached a settlement compute is permanent**.

> Doc: `docs/decisions.md:325` — *"either party can terminate unilaterally"*

### A-13 · The reference concluded event is unreadable **and** mis-computed · `reported`
`GET /events/…e2/settlements` → **500** for operator and performer alike: the seeded
`settlements.computed` jsonb uses `cashHeld` and omits `participantId`/`held`, failing response
validation (`settlement.ts:34-41`).

Its figures are also wrong: the fixture splits 70% of **gross revenue**; the spec splits 70% of
the **pool** (revenue − external costs). The engine is right and the fixture is wrong — a
6 300.00 SEK difference on the platform's reference settlement.

### A-14 · Cross-event budget references are accepted, then permanently 500 the settlement · `reported`
`POST /budgets/:id/lines` validates only UUID *shape*; the FKs are not event-scoped. A
`collectedBy` pointing at another event's participant is accepted (201), after which
`POST /settlement/compute` returns 500 forever — the cash raises the pool but is attributed to
nobody, so `assertBalanced` throws.

Trivially produced by sending a *profile* id where a *participant* id belongs. Same route: a
non-existent participant → 500 (raw FK violation), `{"amount":"abc"}` → 500 (uncaught `BigInt()`).

## P3 — Boundary and spec violations

### A-15 · `deal.type = "custom"` is still creatable · `verified` `corroborated`
Both docs removed it, and `PLAN.md:139` says why — *"free text broke the engine"*. Still present
in `packages/db/src/schema/enums.ts:87` and `apps/api/src/routes/deals.ts:17`.
`POST /events/:id/deals {"type":"custom"}` → **201**.

> Doc: `PLAN.md:139`; `docs/decisions.md:459`

### A-16 · Representations accept any account kind on either side · `reported`
No kind check in `POST /representations`. Accepted: agent→**team_and_crew**, agent→operator, and
an **operator profile as the agent side**. The crew case was driven end-to-end: proposal →
accept → `delegatable-events` → assignment, leaving a delegation flag on the crew participant.

This crosses the line `story.md` uses to *define* the two kinds — crew are *"paid a **fixed
fee** — contrast the **agent**, who takes a percentage of someone else's income"*.

> Doc: `docs/agent-representation.md:18,44`; `docs/story.md:57-60`

### A-17 · The disjoint-region constraint isn't enforced at accept · `reported`
`assertDisjoint` runs in `POST /representations` and the `counter` branch, never in `accept`, and
there is no DB constraint. Two representations proposed while both inactive then both accepted →
**two active agents on `DE` at two different commission rates** (1000 and 2500 bp).
`autoAssignAgentOnPerformerJoin` iterates all active reps, so both get assigned and two
commissions derive off the same entitlement.

> Doc: `docs/agent-representation.md:33,100`

### A-18 · Commission terms are unvalidated free text · `reported`
`commissionableBasis` is `z.string().optional()`, `region` a bare `z.array(z.string())`,
`commissionRate` a bare `z.number().int()`. Accepted: **99% commission on
`"merchandise_and_publishing"`**, a negative rate, and regions `["ATLANTIS","sweden",""]` — where
`"sweden"` silently matches nothing, so the territory looks set but is inert.

> Doc: `docs/story.md:69` — commission is *"**never** on merch or non-live revenue"*;
> `docs/decisions.md:303`

### A-19 · Future-dated termination takes effect immediately · `reported`
The route sets `status='terminated'` and unassigns in the same transaction regardless of
`terminatedEffectiveAt`. A termination dated 2027-06-01 flipped status ~9 months early, and the
agent stops receiving new events during a notice period they are still contractually working.

> Doc: `docs/decisions.md:325-326` — *"effective-dated (immediate or **agreed-future**)"*

### A-20 · Free-tier event cap is bypassable · `reported`
The gate (`apps/api/src/routes/events.ts:202`) fires only on `status === "confirmed"`. At the cap,
`PATCH {"status":"confirmed"}` → 403 ✅ but `PATCH {"status":"concluded"}` → **200**, and
cap-status then reports `used: 4, limit: 3`. The only real monetization limit is one field value
away from unenforced.

> Doc: `PLAN.md:613` — *"**confirm/conclude** event when COUNT ≥ cap → blocked"*

### A-21 · No `grant_admin` entitlement gate on participants · `reported`
`canUseFeature(…, "grant_admin")` is wired only in `routes/profiles.ts:504,566`;
`routes/participants.ts` never calls it. A free-tier operator assigned `operator_full` to a
performer, who then successfully renamed the event.

> Doc: `PLAN.md:656`, `PLAN.md:615`

### A-22 · Public pages serve `draft` and `cancelled` events and accept RSVPs · `reported`
`apps/api/src/routes/public.ts:150,195` filter on `published` only; status is never consulted, and
`POST /publish` has no precondition. A draft event with no date was published and served; after
`PATCH {"status":"cancelled"}` it still returned 200 and **still accepted RSVPs**.

> Doc: `PLAN.md:620` — *"**published+confirmed** events"*

### A-23 · Any participant can author a setlist · `corroborated`
`PUT /events/:id/setlists` (`apps/api/src/routes/setlists.ts:99-101`) authorizes on
`schedule.view`, which every participant holds. Crew and agent both wrote setlist rows (200).
Reads *are* correctly party-scoped, and there is no route to *share* a setlist — the mechanism
that is supposed to be the crew's only access.

> Doc: `PLAN.md:412`; `docs/decisions.md:628`

### A-24 · Outgoing offers are anonymous and pitchless · `reported`
`CreateOfferBody` is only `{targetProfileId, wantedDate, offerFeeMin, offerFeeMax}`; the insert
writes none of `contact_name` / `email` / `artist_name` / `pitch`, and the response has no
`senderProfileId`. The venue's inbox shows a bare date and fee range with no idea who is offering
— and **no field exists through which an agent can name the performer it offers on behalf of**.
The seeded rows show the intended shape, so this is the write path, not the model.

> Doc: `docs/decisions.md:593`

## P4 — Spec'd but not built

### A-25 · The web app is operator-only · `verified`
One static `NAV` array (`apps/web/src/shell/AppShell.tsx:37`), **zero kind branches in the shell**,
and no `/representation` or `/setlists` routes in `apps/web/src/router.tsx` — while
`apps/api/src/routes/representations.ts` and `routes/setlists.ts` are fully built.

The four kind checks in the entire web app are all about *creating events*. The `agent` account
kind — decisions #14, the largest product addition — has a complete backend and **no reachable
UI**.

> Doc: `docs/ui-handoff.md:49-76` (four nav sets, `representation` route rendering Roster / My
> Agent); `PLAN.md:42`

### A-26 · Territory / market scoping is entirely absent · `corroborated`
No `markets` table, no country→market mapping, no `market` on the principal
(`packages/auth/src/principal.ts`), no country predicate in any list query, and no `country`
column on `profiles` or `events`. The only trace in the codebase is a comment.

Discovery and every list query are global; the "cross-market is isolated" guarantee simply doesn't
exist. (`representations.region` country matching **is** implemented correctly — it is only the
platform-wide boundary that is missing.)

> Doc: `docs/decisions.md:554-587` (#17, marked RESOLVED — the most recent architecture decision)

### A-27 · Crew availability → event staffing not started · `corroborated`
The only model is `profile_unavailability` (blocked days), so *"marking yourself available"* isn't
even expressible. No join against events, no notification, no assign path. This is Ran's fix-list
#8, already tracked in ClickUp.

> Doc: `docs/decisions.md:597`

### A-28 · The three per-kind `_details` tables don't exist · `corroborated`
`venue_details`, `performer_details`, `team_and_crew_details` — none exist, though
`packages/db/src/schema/identity.ts:57` still carries the comment saying queried-across fields
live in them. `profiles.details` is `z.unknown()` and is omitted from public profiles and search.
Consequence: `GET /profiles/search` filters by kind and name only; the team-and-crew marketplace
has no queryable surface.

> Doc: `PLAN.md:305,346-347,544`

### A-29 · No plan tier for `agent` or `team_and_crew` · `reported`
`plan_tier` (`packages/db/src/schema/enums.ts:176`) has four values, none for the two newer kinds;
`apps/api/src/lib/entitlements.ts:44` falls them through to `free_operator`, so an agent inherits
the operator event cap.

### A-30 · The #16.4–16.8 event model is unbuilt · `reported`
- **#16.4** — `event_start_time`/`event_end_time` as *required explicit* columns bound to schedule
  items: the schema still has four **nullable** time columns, no binding, no `custom_label`, and
  no seeded default schedule (`GET /schedule` on a fresh event → `[]`).
- **#16.5** — `schedule_items` has no `visibility` and no stage/room; `POST /tasks` silently drops
  `stageId`/`room`.
- **#16.6** — `age_restriction`, `event_type`, `mood_style_tags` don't exist; `POST /events`
  accepts and **silently discards** all three.
- **#16.7** — accommodation/logistics: nothing.
- **#16.8** — the budget is **not** snapshotted at finalize, so planned-vs-actual is lost once a
  budget is superseded — which undercuts the #16.9 analytics surface.

### A-31 · `stages` is a dead table · `corroborated`
Defined at `packages/db/src/schema/events.ts:70` (venue-owned), but `grep 'schema.stages'` over
`apps/api/src` finds **nothing**. Neither the event-scoped routes (`PLAN.md:657`) nor the
profile-scoped ones (`docs/api-routes-plan.md:52`) exist — yet `POST /events` accepts a `stageId`,
so an event can reference a stage no API call can create. Festivals are a first-class operator
type.

### A-32 · `performance_reports` is a dead table · `reported`
Defined at `packages/db/src/schema/content.ts:125`; no route, no read, no write. The
"Performance Reports" screen (`apps/web/src/routes/Reports.tsx:200`) is built from
`useGetApiV1Events()` alone. The setlist → PRO filing derivation doesn't exist.

### A-33 · Off-platform parties can comment but never approve · `reported`
`apps/api/src/routes/shares.ts` registers `/comment` but no `approve` or `confirm`.
`settlement_approvals` is written only from the authenticated route. Sign-off by an off-platform
party is the point of the share flow.

> Doc: `PLAN.md:684`; `docs/off-platform-access.md:109-112`

### A-34 · Idempotency keys missing on three named endpoints · `reported`
`withIdempotency` is absent from `POST /invoices/:iid/issue` (consumes a **gapless** number),
`POST /offers`, and `POST /events/:id/notify` (a Brevo send). Also optional on
`settlement/compute` and `finalize` — three key-less finalizes produced snapshot versions 1, 2, 3.

> Doc: `docs/decisions.md:176-186`

## Cross-cutting observations

- **The balance check can't catch distribution errors.** `Σ net = 0` is necessary, not sufficient.
  A-01 is invisible to it, and A-14 is the only settlement bug it *does* catch — by 500-ing.
- **Unit tests pass while the system is wrong.** The settlement suite builds inputs in the
  engine's preferred shape; the mismatch (A-01) lives in the *mapping* between stored data and the
  engine, which nothing tests.
- **Authorization is split across layers despite the skill saying it never should be.** A-04 is a
  bespoke role check that bypasses the capability engine entirely, and it's the one that lets a
  support act cancel a show.
- **The API has no logs.** `buildApp` sets `logger: false`, so every 500 above arrives with an
  empty payload. Several findings needed the query reproduced by hand to diagnose.
- **The seed is not idempotent under foreign references.** After the audit, `seed:e2e` failed with
  an FK violation because audit-created rows referenced seeded ones. Recovery was to drop the
  container.

## Environment caveats

- Five auditors shared one database and mutated it concurrently; individual findings were each
  re-verified against a live response, but absolute counts (e.g. event totals) drifted.
- The seeded `operator` account has `is_admin = true` — the *only* seed user that does — so
  operator-side results are not a clean operator test. The admin guards themselves are correct.
- `profile_locations` has exactly one row, so cross-region/market behaviour was unprobeable by
  construction.

## Not tested

Web UI beyond the nav audit; payment rails / Pay-All / escrow (deferred by `docs/payments.md`);
`agent_collects` payout redirect; escalators, bonuses and VAT (no schema columns or API fields
exist to set them); off-platform share-token settlement access; the AI/assistant layer (#16.14,
explicitly deferred until manual flows work).

## 2. §25.9.7 — a signature clears when that party's own figures move — **HOLDS**

Four signatures taken on `…e1`: Neon (`performer.b`), Priya (`professional`), Northlight (`co.host`),
and Marlo — **signed by `agent`**, because `performer.a` is delegated and correctly answered
`403 Missing capability: settlement.confirm` on her own line (#14).

| step | what moved | signatures after |
|---|---|---|
| recompute, nothing changed | nothing; `settlements.version` did not bump | **all 4 survive** |
| cost `123,400` with `costSplit {b1:10000}` — borne 100% by the host | only `b1`'s entitlement (`−650,000 → −773,400`); every other row byte-identical | **all 4 survive** |
| reopen deal `e2ad…`, guarantee `400,000 → 500,000`, re-sign, recompute | Priya `900,000 → 1,000,000`; Lantern `−773,400 → −873,400` | **Priya's approval row GONE**; Marlo, Neon, Northlight survive |

`figures_changed_at` moved only for Priya and Lantern in the third step (`06:55:54`, against
`06:52:06`/`06:53:52` on the untouched rows). Σ net stayed `0` throughout.

**The boundary of "a cost edit elsewhere must not clear anybody", measured.** A cost that lands on
the **pool** does move every percentage party's own entitlement, and it clears them — correctly, by
the rule's own definition. Measured: three signatures re-taken, then a **SEK 100** pool cost
(`amount 10000`, no payee, no split) and one recompute → **all three cleared**. So the clause holds
as *"a cost nobody's entitlement moves with"*, not as *"any cost edit"*. This is §25.9.7's recorded
risk, and on a 100%-door-split event it is real: any pool-cost correction re-opens every signature.
Priya's **objection** was not cleared by any of these recomputes, which is what the code says it
intends.

### F-2 · MAJOR — a participation invitation to a cancelled event can be declined by the API and nowhere on screen
**As:** performer.b (Neon Tide), invited to the cancelled Winter Gala, participation `invited`.
**Steps:**
1. `/events` → the invitations card. 2. `/requests` → *Pending*. 3. `/requests` → *All*.
4. Dashboard → *"Answer Winter Gala … this show is off"* → press **Answer**.
**Expected:** §25.9.9 keeps declining open on purpose — *"declining stays open… the answer they are
most likely to want, and the one that closes the invitation rather than leaving it open for ever"* —
and `EventInvitationsCard` was written to render exactly that (`Decline` always, `Accept` only when
`requestStatus !== "cancelled"`).
**Actual:** the row is not on the Events card or the Requests *Pending* tab at all; on *All* it
appears with the `Cancelled` badge and **no buttons**; the Dashboard's Answer lands on
`/requests` *Pending*, where the row is absent. There is **no Decline anywhere in the app** for this
invitation, while `POST /events/…e5/participation/decline` answers `200`.
**Evidence:** `GET /me/event-invitations` as `performer.b` returns the row with
`"requestStatus":"cancelled","answerableByYou":true`; `apps/web/src/hooks/useEventInvitations.ts`
filters the card's list with `all.filter((one) => one.requestStatus === "pending")`, and a cancelled
night's `requestStatus` is `"cancelled"` (the API crosses the event status in — QA5-2), so the row is
dropped before it reaches the component. The *All* tab passes `actionable=false`, hence no buttons.
**And the same filter makes the §25.9.9 guard in that card dead code:** *"Accept is gone"* is TRUE on
this surface, but for the wrong reason — the row never renders, so `requestStatus !== "cancelled"` is
never evaluated. Right answer, wrong mechanism.
**Scope:** the token-invitation surface is unaffected (its landing page is correct, above), so this
bites the party who was added to the event from the roster rather than invited by email. The filter
pre-dates §25.9.9 (run 5's `requestStatus` crossing), so it is a screen half that was built against
an assumption nobody checked, not a regression in `780ab35`.
**One-line fix, for the record and NOT applied:** widen the hook to
`one.requestStatus === "pending" || one.requestStatus === "cancelled"`, which is the exact predicate
the card's own Accept guard already expects to be asked.

### [MAJOR] Settlement — "Flag a dispute" un-finalizes a locked settlement, rewinds the progress rail past Finalized, and hands the signature button back

**As:** `operator@` on the Album Release (`e2e00000-0000-4000-8000-0000000000e1`); reproduced by
`performer.b@` on the same event.

**Steps**
1. As `operator@`, run the settlement, Send for review, take a comment, Add revision, **Finalize**.
   The confirmation dialog reads, verbatim (`EventSettlement.tsx:689`):
   > *"The figures freeze into an immutable record and the exchange rates that produced them are
   > locked to it. **After this the settlement cannot be recomputed and cannot be un-finalized — not
   > from this screen and not from the API.** Transfers can still be marked paid."*
2. Stay on the Settlement tab. **"Flag a dispute" is still drawn**, beside the green
   *"Finalized — figures and rates locked"* pill (`EventSettlement.tsx:793`). Press it — or
   `POST /events/:id/settlement/status {"status":"dispute"}`.
3. Re-read the screen. Then press **Approve**.

**Expected.** Whatever the product rule about disputing frozen figures, *finalized* is a fact the
app has just promised is permanent, in those words. `LOCKED_SETTLEMENT_STATUSES` gates recompute,
re-issue and — since `ca08a8e`/`3c65b41` this week — `signableByYou`. A control that moves the row
out of `finalized` walks around all three.

**Actual.** 200, and the row is no longer finalized:

```
$ api-as operator POST /events/…e1/settlement/status '{"status":"dispute"}'
  200 {"status":"dispute","updated":1,"emailed":[]}
$ select coalesce(p.name,'(commission)'), s.status from settlements s … where event_id='…e1';
   The Lantern Hall     | dispute      ← was finalized 90 seconds earlier
   Marlo Vance          | finalized
   Neon Tide            | finalized     (…and later: dispute, see Scope)
   Priya Sound          | finalized
   Northlight Presents  | finalized
   Astra Booking Agency | finalized
   (commission)         | finalized
```

and on the operator's own screen:

- the header badge reads **Dispute**, not Finalized;
- the **rail rewinds**: `✓ Open · 2 Pending review · ● Comments received · 4 Revised · 5 Finalized`
  — *Revised* and *Finalized* become dim, **unvisited future stops** on a settlement finalized
  minutes earlier;
- **two contradictory pills render side by side**: *"Disputed — a party has objected to these
  figures"* and *"Finalized — figures and rates locked"*;
- **Approve comes back**, and the route accepts it:

```
$ api-as operator POST /events/…e1/settlements/a6a30037…/confirm '{}'
  200 {"id":"892c3fcb-…","approved":true}          ← a signature on figures that were locked
```

The two operators then disagree about the same night: the host's `/settlements` list reads
**Dispute** for the Album Release while `co.host@`'s reads **Finalized**, because only the
disputing party's row moved.

**Evidence:**
`docs/screenshots/qa-2026-10-01-run16/operator-dispute-unfinalized-two-pills.png`,
`docs/screenshots/qa-2026-10-01-run16/performer-dispute-rewinds-finalized.png`, the two `api-as`
calls above and the SQL. The immutable record itself is safe — `settlement_snapshots` still holds
`"status":"finalized"` for all seven rows with `finalized_at 2026-09-29 17:08:54` — so this is a
*status and display* fault, not lost money.

**Scope.** Every party, not only operators. `performer.b@` (a plain performer, no operator
capability) did the same thing to its own row:

```
$ api-as performer.b POST /events/…e1/settlement/status '{"status":"dispute"}'  → 200, updated 1
$ api-as performer.b GET  /events/…e1/settlements  → 9c3b7582 dispute signable True
```
and its screen shows no *"Finalized — figures locked"* pill at all — it simply denies the
settlement was ever finalized. An agent can do it for its act too (`scopedRows` includes live
delegations). Reproduces on any finalized settlement.

**The allowance itself is deliberate and old** — `routes/settlement.ts:2949`: *"A DISPUTE may be
raised over frozen figures — that is precisely when a party most needs to say the number is wrong,
and flagging it changes no money"* (`94adc8f`, long before this week). **The defect is that it is
implemented by overwriting the one column that records finalization**, so the promise, the rail,
the pill and this week's `signableByYou` withdrawal all fall over together. The two defensible
fixes: **(a)** keep `finalized` and carry the objection in a separate field (`settlement_approvals`
already has a `declined` row proposed in §25.6), so the rail and the lock survive; or **(b)** keep
the status move and stop promising permanence — drop the dialog's sentence, keep the rail's
Finalized tick from the feed rather than from `status`, and withdraw the Approve button on any row
with a `settlement.finalized` row behind it. Doing neither is the state today.

### [MAJOR] Settlement — the operator's own rail says a stage never happened, because one press of "Send for review" writes one feed row per party and the feed's page is 20

**As:** `operator@` and `co.host@` on the Album Release.

**Steps**
1. Compute the settlement on an event with **six parties**. Send for review → one party comments →
   Add revision → Finalize. That is four operator actions.
2. Open the Settlement tab and read the rail; open Comments and read Revision history.

**Expected.** `settlementDocument.ts:107-160` is explicit that the rail exists so it *cannot*
understate: *"a page of twenty mixed rows loses the oldest settlement transition … and an unlit
stop that did happen is a second way of being wrong"*, so the rail asks the feed **by type**
(`SETTLEMENT_STAGE_ACTIVITY_TYPES`) rather than filtering a mixed page. `EventSettlement.tsx:1268`
passes that list and **no `limit`**, so the feed's default page of 20 applies.

**Actual.** `5fd1826` changed the status route from **one row per event** to **one row per
settlement**, which is what made the party seats correct (§3) — and multiplied the operator's own
feed by the number of parties. Four actions produced **21 rows** in the rail's own query, and the
page is 20:

```
one press of "Send for review"   → 6 × settlement.pending_review
one party comment                → 6 × settlement.comments_received + 1 × settlement.commented
one press of "Add revision"      → 6 × settlement.revised
                                   = 19 + 2 operator comments = 21 rows, limit 20

$ api-as operator GET "/activity?eventId=…e1&typePrefix=settlement.,transfer."
  items 20   nextCursor true          ← and the panel offers no way to fetch the next page
  {'settlement.finalized':1,'settlement.revised':6,'settlement.commented':3,
   'settlement.comments_received':6,'settlement.pending_review':4}   ← 2 of 6 already gone
```

Carry the same review conversation on (ten more remarks — ordinary for a disputed settlement) and
`settlement.pending_review` **falls off the page entirely**:

```
$ api-as operator GET "/activity?eventId=…e1&typePrefix=settlement.pending_review,
                       settlement.comments_received,settlement.commented,settlement.revised"
  items 20  {'settlement.commented':12,'settlement.revised':6,'settlement.comments_received':2}
                                                     ← zero pending_review rows survive
```

and the operator's rail then reads, on a **finalized** settlement it sent for review itself:

> `✓ Open — ② Pending review — ✓ Comments received — ✓ Revised — ● Finalized`

An unlit stop between two ticked ones. This is run 15's MAJOR, in the seat its fix did not consider.

**The second half of the same change** is that four actions now print **21 near-identical lines** in
the Revision history — *"Figures sent out for review"* ×6, *"Comments came back on these figures"*
×6, *"Figures re-issued after review"* ×6 — with nothing on screen distinguishing them. `5fd1826`'s
message anticipated the objection and answered it with *"`from`/`to` travel so those rows are
distinguishable by their own transition"*; one press gives all six rows the **same** `from`/`to`,
and the detail renderer's whitelist prints neither, so on screen they are six copies of one
sentence. Confirmed in the co-host seat too.

**Evidence:**
`docs/screenshots/qa-2026-10-01-run16/operator-rail-pending-review-unlit-after-truncation.png`,
`docs/screenshots/qa-2026-10-01-run16/operator-revision-history-twelve-lines.png`, the two
`api-as.mjs` reads above, and `select type,count(*) from activity_log where event_id='…e1' and type

pending_review 6 · revised 6`.

**Scope.** Operators only, and it scales with the bill: 4 stage types × N parties. A three-party
event never truncates; a six-party event truncates on the **first** pass. Party seats are unaffected
(each sees ~6 rows — §3), which is why this is invisible from a performer's screen. The rail is

**Expected.** The badge exists (`c8f1446`, run 14's finding) so the operator can see *whose consent
is stale* before finalizing. Its field doc says the signal is safe because *"`sameStoredBreakdown`
guards the write"* (`routes/settlement.ts:257`), and the write loop really does skip an unchanged
row (`:1699`).

**Actual.** Priya's money never moved and the badge fires anyway:

```
before: Priya  entitlement 400000  net 400000   version 2  updated_at 17:42:42.300
after : Priya  entitlement 400000  net 400000   version 3  updated_at 17:44:36.534
roster: "Priya Sound · Crew · Signed off · Figures changed since"
```

The cause is that the **ladder travels inside every party's stored breakdown** —
`"ladder":{"costs":"2650000","revenue":"5500000","netRevenue":"2850000","adjustedNet":"2850000"}`
sits in Priya's `computed` — so any cost edit anywhere makes `sameStoredBreakdown` false for
**every** row, bumping `version` and `updated_at`, and `figuresMovedSince` is
`updatedAt > approvedAt` (`:2455`).

A control run confirms the guard itself works: a **no-op** recompute (nothing edited) moved no
`updated_at` at all.

**Evidence:** `docs/screenshots/qa-2026-10-01-run16/roster-figures-changed-on-unchanged-party.png`;
the two SQL snapshots; `select computed from settlements where id='8173f0e3…'` showing the ladder.
**Scope.** Every signed party on every event where any budget line is edited after a signature. It
errs safe (over-warns, never under-warns), which is why it is MINOR — but it is the signal that
exists to stop a wrong finalize, and it now fires on every party every time.

   Recalculate, and Planned-vs-actual still read 11,000 with nothing written to Postgres. The
   control commits on **focusout**, and a synthetic `new Event('blur')` does not bubble as one.
   Re-run with `FocusEvent('focusout')` it committed immediately and the whole planned/actual

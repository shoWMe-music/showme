### [BLOCKER] Money spine — a solo operator's costs never reach the settlement; the night settles with revenue and no costs

**As:** operator (The Lantern Hall), on an event with no co-host — the commonest shape there is.

**Steps:**
1. On `Open Mic Wednesdays` (one operator, no co-host), open the **Budget Planner**. There is no
   "Shared ledger / My budget" chooser — the operator is given one book and no indication of which.
2. Type a cost into it: **Production cost SEK 1,000**.
3. Sign the deal, then open the Settlement and press **Run the settlement**.

**Expected:** the settlement is "a copy of the budget" (the product owner, 2026-08-27, quoted at
`routes/settlement.ts:723`). The cost the operator entered is a cost of the night, so the waterfall
should read Gross 6,300 − Deductions 1,000 = Net 5,300, and the 70% act should be paid
`max(2,000, 70% × 5,300)` = **SEK 3,710**.

**Actual:** the settlement imported the two ticket tiers and **nothing else**. Deductions **SEK 0**,
adjusted net SEK 6,300, Marlo paid **SEK 4,410**, operator residual SEK 1,890. The SEK 1,000 the
operator typed is nowhere in the reconciliation.

**Why it happens:** `ensureEventBudgets` (`apps/api/src/lib/budget-provisioning.ts:83`) gives a
**solo** operator only a `private` budget and deliberately creates **no shared ledger** — *"A solo
operator has nobody to reconcile with, so a shared budget would just be a second empty book."* But
both readers downstream take the **shared** budget and only the shared budget:
- `copyBudgetOnce` (`apps/api/src/lib/settlement-lines.ts:79`) — so no cost is ever copied;
- `useBudgetSeed` (`apps/web/src/components/useBudgetSeed.ts:731`) — so the same costs never reach
  `doorForecastFrom` either (see MAJOR-2).

`seedTicketTiersIntoBudget` then **creates** a shared budget to put the Event Details tiers in
(`settlement-lines.ts:243`), which is why revenue arrives and costs do not. Verified in Postgres
after the run:

```sql
select b.scope, bl.kind, bl.label, bl.amount
  from budgets b join budget_lines bl on bl.budget_id = b.id
 where b.event_id = 'e2e00000-0000-4000-8000-0000000000e3';
  private | cost    | Production cost | 100000     ← the operator's own entry
  shared  | revenue | Door entry      | 480000     ← created by the settlement
  shared  | revenue | Advance         | 150000     ← created by the settlement

select kind, label, amount from settlement_lines where event_id = '…e3';
  revenue | Door entry | 480000
  revenue | Advance    | 150000       ← two rows. No cost.
```

**Scope:** reproduces on any event with exactly one operating profile, which is the default shape of
a venue planning its own night. It does **not** reproduce on the seeded Album Release, because
Northlight Presents co-hosts it and the seed therefore gave it a shared ledger — which is why the
branch's own end-to-end verification did not meet it. The Budget Planner offers no scope chooser at
all when only one budget exists, so the operator is never told their work is in a book the
settlement does not read.

**This is the exact mirror of the bug `a033436` closed.** That commit fixed "costs and no revenue";
this is revenue and no costs, reached from the same two rules failing to meet.

**The one-line fix is not one line — it is a product call.** Either `ensureEventBudgets` provisions
a shared ledger for a solo operator too (and the planner opens on it), or the planner's single-book
view writes to the shared scope when there is no co-host. Picking is Daniel's.


**RESOLVED 2026-09-26 — provisioning was inverted, and PLAN.md already said so.**
Daniel's call: a solo operator's one book should behave exactly as the two-operator
case does, which is the role the SHARED ledger plays. PLAN.md:215 states it —
*"Co-promoters share **one** budget; each operator **may also** keep a **private**
budget"* — so the ledger is the event's book and a private one is the optional extra.
`ensureEventBudgets` had that backwards for a solo event.

- **The event always has a shared ledger**, co-hosted or not. A `private` book is now
  provisioned only once there IS a co-host to keep it from, so a solo operator has
  exactly one book, sees no scope chooser, and it is the book the settlement copies.
- **Migration `0046`** relabels an existing solo event's private budget as its ledger
  rather than provisioning an empty one beside it — which would have left everything
  already typed exactly as stranded, one click further away. Narrow by four clauses:
  one operating profile, that profile owns the book, the book is private, the event has
  no ledger yet. A co-hosted event's margin books are untouched.
- **Both seeds moved too.** `Nordic Synth Showcase` shipped the broken shape (one
  operator, a `private` book), which the migration cannot heal because seeding runs
  after migrations.

Proven live on this exact repro, not from tests: the solo read now returns one
`shared` book, and after typing the same SEK 1,000 production cost the settlement
reads **Gross 6,300 − Deductions 1,000 = Net 5,300** where it read Deductions SEK 0
before (`screenshots/qa-2026-09-26/qa-fix-settlement-solo.png`). Regression tests
cover both halves — a solo operator's cost reaching the settlement, and a co-operator's
private margin book still staying out of it — and the first of them fails against the
old provisioning, which is the only reason to believe it. API suite 1271 passed, e2e
112 passed.

This also closed the MAJOR below about the planner's door forecast reading nothing for
a solo operator: `useBudgetSeed` reads the shared budget's lines, and there now is one.

### [MAJOR] Budget Planner — the derived performer fee is fixed in the break-even model, so break-even is wrong wherever a percentage deal exists

**As:** operator.

**Steps:** open the Budget Planner on any event carrying a percentage deal and read
**Break-even tickets** and the Break-even analysis chart.

**Expected:** `packages/shared/src/budget-planning.ts:289` states the rule the block was rewritten
to obey — *"Every term that moves with attendance has to be evaluated at the attendance being solved
for."* A `door_split` or `guarantee_vs_door` fee is precisely such a term: the row above it moves
with attendance and says so.

**Actual:** `enteredCosts = sum(inputs.costs)` (`budget-planning.ts:277`) and the derived fee is in
`inputs.costs` — `useBudgetEditor.ts:2345` passes `editor.costs`, which includes the `readFromDeal`
row. The fee is therefore held at its value at the *planned* attendance while ticket sales are swept.

Measured on the Album Release, a **100% of adjusted net** door split:

| Advance qty | Fee shown (moves ✓) | Break-even tickets | Capacity |
|---|---|---|---|
| 260 | SEK 50,000 | **325** | 400 |
| 360 | SEK 75,000 | **427** | **400** |

At 360 the screen advertises a break-even the room cannot physically reach, and the chart caption
reads *"Revenue passes total cost at 427 tickets of 400 capacity."* Both numbers are reproducible
from the fixed-fee model: 427 solves `259.4N = 108,000 + 0.015 × 259.4N`. The true answer on a 100%
door split is that **there is no break-even at any attendance** — the act takes everything left
after costs, so the operator's profit is `−processing` whatever sells.

On Open Mic (70% guarantee-vs-door, no other costs) the screen says **61 of 80**; solving with the
fee actually moving gives ~28. More than double.

**Evidence:** `docs/screenshots/qa-2026-09-26/openmic-draft-fee-and-breakeven.png`; the table above,
each row read off the live planner after the write flushed.

**Scope:** every event with a `door_split` or `guarantee_vs_door` deal. Does not affect a flat
guarantee, where holding the fee fixed is correct.

### [MAJOR] Budget Planner — a deduction and a non-operator's revenue move the forecast but not the engine

**As:** operator. **Found by reading, confirmed against the two implementations; not driven to a
settled number, so filed as a divergence rather than a measured loss.**

`doorForecastFrom` (`useBudgetSeed.ts:648-676`) builds the base the fee is derived from as
`totalRevenue − sheetCosts − rentals`, where

- `sheetCosts` = **every** cost line without a `deal_id`, at its **full** amount;
- `sheetRevenue` = **every** revenue line, whoever collects it.

`reconcile()` does neither:

- `costBearingOf` (`packages/settlement/src/cost-bearing.ts:69`) gives a line with
  `payee_participant_id` `poolShare: 0n` — a deduction lowers **that party's entitlement**, never the
  pool. The planner subtracts it from the base anyway, so a deduction lowers the forecast fee twice
  and the settled fee once.
- `reachesThePool` (`packages/settlement/src/revenue-shares.ts:86`) excludes a revenue line the venue
  or the act collected. The planner counts it, so a venue-run bar inflates the forecast base.

Both are the same class of defect the branch exists to remove — the planner and the engine
disagreeing about what a percentage is a percentage of (#23, #24.1). The comment at
`useBudgetSeed.ts:452` states the intent plainly: *"the bar an operator reads while planning has to
be the arithmetic that settles later."*

**Scope:** any sheet using the "To be deducted from" column or a non-operator collector — both are
first-class controls on the Costs and Revenue cards.

### [MINOR] Deal, planner and settlement give the split base three different names

The deal form and the agreement card label the percentage **"Share of the pool (%)"**; the planner's
derived row says **"100% of the adjusted net"**; the settlement's waterfall says **"Adjusted net —

"share of the pool" is not a synonym — it names the wrong one. Given that #23 and #24 are entirely
about what the percentage is *of*, four vocabularies on one journey is the drift decisions.md exists
to stop.

### [MINOR] The Settlements tiles contradict each other and mislabel `open` as "Pending review"

`settlementDocument.ts:497-502` defines `settled = status === "paid"`, `pending = open ||
comments_received`, `outstanding = status !== "paid"`, `finalized = status === "finalized"`. On the

Two problems, both wording rather than arithmetic:
- **"Total settled SEK 0" beside "Finalized SEK 20,700"** — a finalized settlement reads as settled

The filter chips are consistent with the tiles (verified: "Pending review" returns the Open row,
"Finalized" returns Spring Warmup, "Paid" returns *"No settlements match this filter"*), so this is
a naming defect, not a filtering one.

## Probes that lied — and what the re-run showed

Four, and they are the reason to trust the rest.

1. **"A performer cannot sign their own deal" — nearly filed as a BLOCKER, and wrong.**
   `POST /deals/…/confirm` as performerA returned `403 Missing capability: agreement.confirm`, and
   the seeded "Performer — own slice" set really does lack it. I checked the effective capabilities
   before writing it up: **performerB has `agreement.confirm` on the same event and performerA does
   not** — because performerA is *represented*, and decisions.md **#14** delegates signing to the
   agent. The agent then signed, and the deal confirmed. What looked like a product-wide blocker was
   the rule working.

2. **"`event.participant_added` does not publish over SSE."** The operator's open Collaborators tab
   did not refresh when I added Priya, even after nine seconds, and did after a reload. But the
   notification is addressed to the **added** profile's members, not to the watcher —
   `notifyProfileMembers(created.profileId, …)`. Checking Priya's own feed found it:
   `event.participant_added | Added to "Open Mic Wednesdays"`. Delivery works; the operator is simply
   not the recipient.

3. **"Event creation produces an event with no timezone."** True of my first created event
   (`venue_profile_id NULL`, `timezone NULL`) — because I set the venue input's value programmatically
   and bypassed the picker. Typing "Lantern" with real key events brings up a **MY PLACES** list, and
   choosing from it links the venue profile, which is what `resolveEventTimezone` snapshots from. My
   probe, not the app.

4. **"The share document is unreachable / the recipient sees nothing."** Two false readings in a row:
   the OTP is single-use (my second `verify` on a spent code failed), and the session uses
   `Authorization: **ShareBearer** <jwt>`, not `Bearer`. With a fresh code and the right scheme the
   document came back in full — and produced the strongest pass in the sweep.

A fifth, smaller: clicking the "Pending review" filter chip on Settlements appeared to do nothing.
Re-clicking the actual `<button>` showed the filters work correctly. The first click missed.

### [BLOCKER] Deals — an operator can create a deal it then cannot see, and it freezes the night's settlement forever

**As:** `operator@` (The Lantern Hall, the host and the creator), on the Album Release → **Deals**.

**Steps (all in the browser)**
1. `/events/e2e00000-0000-4000-8000-0000000000e1?tab=deals` → **New deal**.
2. Party 1 → **Neon Tide — Performer**, role *Pays*. Party 2 → **Priya Sound — Crew**, role *Is paid*.
   (The picker offers every participant and never requires the operator to be one of them.)
3. Name it, enter a fixed amount, press **Save draft**.
4. Read the Deals tab. Then open Budget Planner. Then Settlement → **Recalculate**.

**Expected.** Either the composer refuses a deal the author will not be able to manage, or the author
retains `deal.edit` on what they created. §25.7.4's whole principle is that *"cancelling and renaming
belong to the CREATOR"*; §25.7.2 built `dealDeletability` explicitly so *"the UI must not offer a
delete the API will refuse"*. And CLAUDE.md already names this exact failure mode — *"an unsignable
agreement that froze a whole event's settlement for as long as it existed."*

**Actual.** The deal is created (`201`), **and then disappears from the creator's screen entirely** —
no card, no toast, no error. The row is in Postgres:

```
a59d9987-8bd1-459a-9571-b30c92410e4e | QA13 browser stuck deal | draft
```

The host's own **Budget Planner** then reads (screenshot
`host-planner-two-of-its-own-deals-withheld.png`):

> "**2 of this event's deals are not shown to you**, so what the night costs is higher than the total
> above. Profit, margin and break-even are left out rather than calculated without them."

…about two deals the host itself created. And **Recalculate** answers (screenshot
`blocker-settlement-refuses-naming-invisible-deals.png`):

> "This settlement cannot open until every agreement on the event is signed: "QA13 browser stuck
> deal" (a59d9987-8bd1-459a-9571-b30c92410e4e) has not been sent to its parties; "QA13 stuck deal —
> Neon Tide pays Priya" (c266d85f-f9dc-46d0-9591-cbfc6b65f84d) has not been sent to its parties. Send
> each agreement and have its parties confirm it — **or cancel one that is no longer happening** —
> then run the settlement again."

It names two raw UUIDs and tells the operator to cancel one of them. The operator cannot reach either.

**Evidence — the full reachability matrix on `c266d85f…` (payer Neon Tide, payee Priya Sound):**

```
seat          GET /deals/:id    PATCH {"status":"cancelled"}   DELETE     POST /deals/:id/send
operator        404               404                          404        404  "Deal not found"
co.host         404               404                          404        —    (operator_full, still not a party)
performer.a     404               404                          404        —
agent           404               404                          404        —
performer.b     200               403 "Missing capability:      403        403  "Missing capability:
                                      deal.edit"                              agreement.manage"
professional    200               403 (same)                    403        403  (same)
```

`GET /deals/:did` is party-scoped, so the two accounts that hold `deal.edit` on the event (host and
full-control co-host) get **404 "Deal not found"**; the two accounts that can read it are a performer
and a crew member, neither of whom carries `deal.edit` or `agreement.manage`. **No account in the
system can send, cancel or delete it**, and `assertEveryAgreementSigned` refuses every future compute.

**Scope.**
- Reproduces from the browser and from the API, on the seeded event.
- It only becomes *unrecoverable* when neither entitled party is represented: my first attempt used
  Marlo (payer) as the counterparty and the **agent** could cancel it (`200`), because a delegated
  performer's `deal.edit` sits with their agency. Any deal between two unrepresented non-operator
  parties is permanently stuck.
- The narrower half — "the host loses sight of a deal it authored" — reproduces on *every* deal the
  operator is not named on, represented or not.

**One-line fixes, as claims about the code (not applied):** the smallest correct change is at the
authoring boundary, not the read boundary — `POST /events/:id/deals` could require the author's own
participant to be one of the parties, **or** `resolveDealAuthority` could treat `deals.created_by`
as a party for management purposes. *Do not* widen `GET /deals/:did` to everyone with `deal.edit`:
decisions #4 and `settlement.ts`'s own comment are explicit that an operator's breadth is emergent
from party membership, and six tests pin that.

### [MAJOR] Settlement — a CANCELLED deal still opens the other parties' settlement figures, permanently

**As:** `professional@` (Priya Sound, `team_and_crew`, permission set *"Crew — schedule only"* =
`{event.view, schedule.view}`), on the Album Release Settlement workspace.

**Steps**
1. Name the crew member an **observer** on any deal on the event (the host can do this from the deal
   composer; I did it on "QA13 observer probe", a Lantern Hall ↔ Neon Tide guarantee).
2. **Cancel that deal.** It now "pays nobody" and is excluded from the engine, from `hiddenCount` and
   from `useBudgetSeed`.
3. Open `/events/e2e00000-0000-4000-8000-0000000000e1/settlement` as the crew member.

**Expected.** story.md's crew boundary: *"They see the schedule and their own deal, never the
budget."* And a cancelled agreement is the one status whose meaning `reconcileEvent`'s own comment
calls unambiguous — *"there is nothing left to reconcile under it."*

**Actual.** The crew member is served **Neon Tide's whole settlement**:

```
$ api-as.mjs professional GET /events/<e1>/settlements
[ { "participantId": "…b3",  "entitlement": "3080000",
    "lines": ["e2e00000-0000-4000-8000-0000000000d1"] },
  { "participantId": "…b4",  "entitlement": "0", "lines": [] } ]
```

and the screen prints it in words:

> "Neon Tide · Performer · **70% of the adjusted net — Neon Tide's 40% of the deal's SEK 77,000** ·
> **SEK 30,800**"

Priya's *only* qualifying `deal_parties` rows on this event are **observer rows on two cancelled
deals** — verified directly:

```
 QA13 observer probe                    | cancelled | observer
 QA13 observer open-editor              | cancelled | observer
 QA13 crew fee paid by the act          | cancelled | payee      (payee does not qualify)
 QA13 stuck deal — Neon Tide pays Priya | draft     | payee      (payee does not qualify)
 QA13 browser stuck deal                | draft     | payee      (payee does not qualify)
```

**Two separate defects in one query.** `partiesVisibleTo` (`apps/api/src/routes/settlement.ts:1257`)
joins `deal_parties → deals` filtering on `deals.eventId` **and nothing else**:

- **(a) No `status` filter.** Every other reader of `deals` on this path excludes `cancelled`
  (`reconcileEvent`'s `ne(schema.deals.status, "cancelled")`, `hiddenCount`'s `paying()`,
  `useBudgetSeed`'s rentals filter). §25.7.2 calls cancelling *"the NORMAL ending for an
  agreement"*, so these grants accumulate over an event's life and never expire.
- **(b) It discloses the counterparty's WHOLE settlement, not the shared deal's line.** The figure
  above (SEK 30,800) comes entirely from deal `d1`, the Album Release Door Split, which Priya is not
  a party to in any role. Observing a SEK 5,000 guarantee discloses a SEK 30,800 entitlement under a
  different agreement.

**Scope.** Reachable for any `payer` or `observer` — `DEAL_ROLES_THAT_SEE_THE_DEAL = ["payer",
"observer"]`. Operators are stripped out afterwards, so the exposure is to non-operator parties:
crew, performers and agents. A realistic seed-shaped case is the act that hires its own engineer —
the engineer becomes an observer or the act becomes a payer, and the counterparty's whole settlement
opens. Not reproducible on the pristine seed, because the seed names no crew member on any deal.

### [MINOR] Notifications — the one "New message" row in the bell is dead text, and the comment above the rule says it is not

**As:** `operator@`, after `performer.b@` posted a message on the Album Release.

**Steps.** Open the bell. Every row is a `<button>` except *"New message on "Marlo Vance — Album
Release""*, which renders as an inert `<div>` — no tab stop, no pointer, no navigation.

**Evidence.**

```js
// rows in the open bell, by tag
BUTTON "Invitation accepted — Nordic Synth Showcase"
BUTTON "Astra Booking signed off their settlement"
BUTTON "Agreement confirmed on \"Album Release — Door Split\""
…
DIV    "New message on \"Marlo Vance — Album Release\""      ← the only one
BUTTON "Booking request from QA13 Clash Band"
```

**Cause, and it is two mismatches, not one.**

- `apps/api/src/routes/messages.ts:401` writes ``link: `/events/${eventId}?tab=messages` ``, while
  `apps/web/src/components/notificationDestination.ts:105` matches
  `EVENT_LINK = /^\/events\/([^/?#]+)$/` — anchored before the query string. The link matches
  nothing, `notificationDestination` returns `null`, and `NotificationRow` deliberately renders an
  unlinked row as a plain `<div>`.
- `TAB_BY_NOTIFICATION_TYPE` keys **`"event.message_posted"`**, but that string is the **SSE frame**
  type (`packages/db/src/notify.ts:411`, `routes/messages.ts:366`) and never reaches the
  `notifications` table. The stored row's type is **`message.posted`**
  (`select distinct type from notifications` confirms it). So that map entry is dead code.

The comment sitting on it states the opposite of both facts:

> "Both deliveries of this type — the stored bell (`routes/messages.ts`) and the realtime one
> (`@showme/db/notify`) — carry the same **bare** event link, so one rule covers both."

This is the same shape CLAUDE.md warns about: a comment asserting a rule the code does not keep.

**Fix, as a claim about the code (not applied):** relaxing the regex to
`/^\/events\/([^/?#]+)(?:[?#].*)?$/` fixes the click for this and any future writer. Dropping
`?tab=messages` from `messages.ts:401` alone would **not** be enough — the type key is also wrong, so
the row would open Event Details rather than Messages. Both halves need touching.

### [NOTE] `sameBreakdown` ignores `residual` and `residualBasisPoints`, so a cost-split change that moves no money is not persisted

Measured: with the residual at **0**, setting `operatorCostSplit` from unset (implicit 50/50) to
**70/30** produced a compute *response* carrying `residualBasisPoints: 7000 / 3000` while the stored
`settlements.computed` kept `5000 / 5000` and `updated_at` did not move.
`apps/api/src/routes/settlement.ts:1418` compares `entitlement / collected / paid / held / net /
lines / ladder` and neither residual field.

**Not user-visible today**, and that is why it is a NOTE: `settlementDocument.ts:649` only renders the
residual rule row when `computed.residual !== "0"`, and any split change that moves a non-zero
residual also moves `entitlement`, which *is* compared. Confirmed by re-running with a real residual:
after `d1` moved to a 70% split, the stored rows read **70% / SEK 23,100** and **30% / SEK 9,900**
correctly, and the co-host's screen said *"Your 30% of what is left after every other party is
paid — SEK 9,900."*

## 5. Probes that lied

Four, and each would have become a wrong finding.

1. **"Saving the display currency does nothing."** Selecting SEK and pressing *Save changes* in one
   `evaluate_script` tick left `users.currency` at `EUR`. Splitting the two into separate calls saved
   correctly. React had not re-rendered between my synthetic option click and the submit — my
   scripting artifact, not a bug. The first (SEK → EUR) direction, done in two calls, had worked.
2. **"`operatorCostSplit` is ignored by the engine — both operators come back at 5000."** The
   *compute response* said `7000 / 3000` in the same breath. The stored rows were stale because
   `sameBreakdown` does not compare the residual fields (recorded as a NOTE above), and the residual
   was 0 so nothing else moved. Making the residual non-zero showed the weighting applied exactly.
   Reading only the database would have produced a wrong MAJOR about the money engine.
3. **"A cancelled deal's disclosure is my own artificial setup."** It partly is — the seed names no
   crew member on any deal — but the shape survives the objection: the only rows granting Priya sight
   of Neon Tide are `observer` rows on **cancelled** deals, and `partiesVisibleTo` has no status
   filter while every neighbouring query does. Re-checked after every later mutation.
4. **"An event-list row does not open the event."** A synthetic `element.click()` on the row did
   nothing; this is run 12's probe-that-lied #5 in a new place (a real pointer sequence is needed).
   I routed around it rather than filing it.

And one near-finding recorded so the next sweep does not chase it: the Budget Planner's payment-
processing assumption (1.5%) is **not** subtracted before the door split, so a 100%-door night shows
`Profit / loss −SEK 2,145` while the acts are paid the full adjusted net. That is consistent —
`splitBase = totalRevenue − sheetCosts − rentals` and the processing fee is a planning *assumption*,
not a budget line, so the settlement never sees it either. Documented behaviour, not a defect.
